# Сервис оптимизации для приложения «Марш!»

Единый сервис с адаптерами OR-Tools Routing 9.15.6755 и PyVRP 0.14.0. Cloudflare Worker подготавливает данные и дорожные матрицы; отдельный Python-процесс запускает выбранный решатель. Приложение восстанавливает километраж из собственной матрицы и независимо проверяет ограничения перед сохранением черновика. Сервис не имеет доступа к базе, адресам, контактам, геокодеру или API карт.

Архитектура и особенности обработки аварий в PyVRP: [единый API оптимизации](../../docs/OPTIMIZER_ADAPTERS.md).

## Запуск

Из корня проекта, Python 3.12+:

```powershell
python -m venv services/optimizer/.venv
services/optimizer/.venv/Scripts/python.exe -m pip install -r services/optimizer/requirements.txt
$env:OPTIMIZER_SERVICE_TOKEN = '<секрет из конфигурации окружения>'
services/optimizer/.venv/Scripts/python.exe services/optimizer/server.py --host 127.0.0.1 --port 8765
```

На Linux путь интерпретатора — `services/optimizer/.venv/bin/python`. Для разработки можно использовать существующее окружение `algorithm-research/benchmark/.venv`; исследовательские скрипты при этом не запускаются.

В серверном окружении приложения задать `OPTIMIZER_SERVICE_URL` и такой же `OPTIMIZER_SERVICE_TOKEN`. Локальный URL: `http://127.0.0.1:8765`; для развёрнутого Worker требуется доступный ему HTTPS-адрес сервиса за reverse proxy. Loopback удалённого Worker не указывает на компьютер разработчика. URL и токен не передаются браузеру. В глобальных настройках планирования выбрать **OR-Tools Routing** или **PyVRP** и политику аварий, затем пересчитать и опубликовать план.

Для сетевого адреса обязательны HTTPS в приложении и токен с обеих сторон. Сам Python-сервер обслуживает HTTP и должен находиться за HTTPS-прокси. Прокси также ограничивает тело запроса, время соединения и доступ к сервису. По умолчанию слушается только `127.0.0.1`; при ином bind без токена сервер не запускается. Установленные настройки и версия политики входят в проверку актуальности черновика.

Добавлена миграция `0017_optimizer_service_policy.sql`. Она сохраняет выбранный решатель и политику отдельно от прежнего ограниченного перечисления БД. Выбор OR-Tools явный: при отсутствии подключения, переполнении сервиса или ошибочном ответе приложение показывает ошибку и сохраняет прежний черновик. Автоматической подмены решателя нет. 21 сентября сервис запущен локально через `scripts/start-local.ps1`, подключён к трём синтетическим подразделениям. Первый опубликованный план: 203/203 заявки, 27/35 бригад, 1284,8 км, жёстких нарушений нет. Матрицы и геометрия получены от действующего OSRM, без пробок. Удалённое развёртывание не выполнялось.

## Цели и ограничения

Каждый следующий критерий применяется после предыдущего:

| Политика | Порядок |
|---|---|
| Обычные заявки | Больше выполненных → меньше уникальных исполнителей → меньше метров |
| `emergency_fast/v1`, по умолчанию | Больше выполненных → больше выполненных аварий → меньше суммарной задержки начала аварий → меньше исполнителей → меньше метров |
| `emergency_staff/v1` | Больше выполненных → больше выполненных аварий → меньше исполнителей → меньше суммарной задержки начала аварий → меньше метров |

В OR-Tools целочисленные веса вычисляются из верхних границ всех младших критериев. Они не могут компенсировать ухудшение старшего критерия. При переполнении безопасного диапазона модель отклоняется. PyVRP использует нативный поиск маршрутов и отдельный прикладной поиск вставок/переносов с лексикографическим сравнением, включая задержку аварий; подробности и границы поиска описаны в документе об адаптерах. Ограниченный по времени поиск **не доказывает глобальную оптимальность**.

- Клиентские окна ограничивают начало обслуживания; окончание обязано укладываться в смену. Несколько окон сохраняются. Начало не предшествует `releaseAt`.
- Все HD, навыки и допуски заявки обязательны. Исполнители других подразделений отсутствуют во входном пуле.
- Матрицы направленные, с отдельным профилем каждого исполнителя. `null` означает недостижимую дорогу. Длительность округляется вверх до секунд, расстояние — до метров.
- Ожидание разрешено. Поездка и работа не пересекают перерыв; можно приехать до перерыва и ожидать клиентское окно после него.
- Старт берётся из подготовленной смены. Обязательного возврата нет; явная конечная точка поддерживается. Ограничения числа заявок, дороги и километража действуют только при передаче во входных данных.
- Неизменяемая заявка может фиксировать исполнителя и начало. Независимый валидатор также проверяет порядок; если решатель его нарушил, результат отклоняется.
- Для неназначенной заявки без компетентного исполнителя есть точная причина. Остальные пропуски описываются как отсутствие места в найденном за ограниченное время плане, без ложного доказательства невозможности.

## Протокол и эксплуатационные пределы

- `GET /health` → `{ "service": "marsh-optimizer", "protocol": 1, "engines": ["ortools", "pyvrp"] }`.
- `POST /v1/solve`, JSON, заголовок `Authorization: Bearer …`. Типы запроса находятся в `apps/web/app/lib/server/planning/service-optimizer.ts`, проверка — `solver.validate`. Поле `engine` выбирает `ortools` или `pyvrp`; неизвестное значение отклоняется.
- Время передаётся целыми секундами относительно общего UTC-начала; расстояния — метрами. Преобразование региональных времён выполняет приложение.
- Один одновременный расчёт; занятый сервис возвращает 503 без скрытой очереди. Размер тела до 32 МиБ, чтение до 15 секунд. Поиск до 60 секунд, отдельный процесс принудительно завершается через 75 секунд. Обычный бюджет приложения — 15 секунд на подразделение.
- Верхние границы протокола: 1000 заявок, 100 исполнителей, горизонт 7 суток. Это ограничения входа, **не обещание производительности** на всех сочетаниях. Матрицы и моделирование перерывов могут исчерпать размер запроса или время раньше.
- Код 422 — неверная модель, 401 — неверный токен, 503 — занято, 504 — превышен общий предел. Ответ `no_solution_found` не считается доказанной невыполнимостью.

Поддерживается одна оставшаяся смена каждого исполнителя в расчёте. Пустое время означает весь выбранный день; заданное время начинает перепланирование с этого момента в регионе подразделения. Начатые, приостановленные и закрытые работы сохраняются. Исполнитель с активной работой участвует в оставшейся очереди только после явной оценки времени освобождения и адреса продолжения. Изменение состояния работы делает оценку устаревшей. Последняя завершённая точка подписывается как известная из выполнения, а не GPS. Уже задействованный исполнитель не увеличивает целевой счётчик персонала при добавлении ему оставшихся работ.

Подтверждённый клиенту визит может получить предложение переноса. Приложение блокирует публикацию до явной отметки диспетчера «Я сообщил клиенту» для каждого изменения, сохраняет автора, время и оба назначения. Сам сервис не подтверждает уведомление клиента. Общие ресурсные пулы пока отклоняются явно. Приложение рассчитывает доступные подразделения последовательно с отдельными пулами и публикует общий результат атомарно. Создание аварии использует признак сохранённой версии HD, высокий приоритет и окно календарных суток региона; ранняя вставка сохраняет ограничения смены, компетенций и полученного оборудования.

До выезда бригада может получить оборудование всех назначений дня. После выезда приложение передаёт в решатель только кандидатов с полным набором требуемых видов оборудования всех HD; независимый валидатор повторяет проверку. Неизвестный полученный комплект не считается подтверждённым наличием. Количества справочные, расход остатков не моделируется. Ручное назначение без оборудования сохраняется с красным предупреждением в приложении.

## Проверка

```powershell
$env:OPTIMIZER_TEST_PYTHON = (Resolve-Path 'services/optimizer/.venv/Scripts/python.exe').Path
pnpm qa
# Только Python, из services/optimizer:
../../algorithm-research/benchmark/.venv/Scripts/python.exe -m unittest -v test_solver test_server
# После успешной сборки Worker, из корня:
node --test apps/web/tests/optimizer-service.test.mjs apps/web/tests/beeline-planning.test.mjs
```

Проверки охватывают реальные OR-Tools и PyVRP, HTTP по loopback, авторизацию, перегрузку и освобождение слота после ошибки, цели, окна, смены, перерывы, недостижимые дороги, компетенции, поддельный ответ и атомарную публикацию. Приёмочный сценарий импортирует подготовленные 204 строки в SQLite в памяти и рассчитывает очередь из 203 заявок по трём подразделениям с уже сохранённой дорожной матрицей исследования. Он не вызывает внешние карты и не меняет исследовательские результаты. Геометрия дорог и рабочее развёртывание этим сценарием не проверяются. Результат: `apps/web/.tmp/beeline-planning-acceptance.json`.

Справочник OR-Tools: [окна времени](https://developers.google.com/optimization/routing/vrptw), [неназначенные визиты и штрафы](https://developers.google.com/optimization/routing/penalties). Постановка приложения: `docs/ALGORITHM_RESEARCH_REQUIREMENTS.md`; фактический прогресс: `docs/IMPLEMENTATION_PLAN.md`.
