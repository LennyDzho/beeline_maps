# Марш!

«Марш!» — система управления выездными работами: от регистрации заявок и ведения справочников до построения маршрутов, публикации дневного плана и выполнения заданий инженерами в Android-приложении.

Система учитывает подразделения, графики, квалификации и допуски исполнителей, оборудование, транспорт, клиентские временные окна и приоритет аварийных работ. Расчёт можно выполнять через OR-Tools, PyVRP или TSP API 2ГИС, а дорожные матрицы получать из 2ГИС либо OSRM.

## Возможности

- единое рабочее место диспетчера с заявками, исполнителями, маршрутами и картой;
- общий план нескольких подразделений, черновик расчёта и атомарная публикация;
- подбор исполнителей по графику, компетенциям, допускам, транспорту и оборудованию;
- защита подтверждённых клиенту визитов от автоматического переноса;
- отдельный Python-сервис оптимизации с OR-Tools и PyVRP;
- Android-приложение инженера с офлайн-очередью, статусами визита и отчётами;
- версионируемые виды работ, аудит действий и операционные уведомления;
- исследовательский стенд для воспроизводимого сравнения алгоритмов маршрутизации.

## Архитектура

| Компонент | Назначение | Технологии |
| --- | --- | --- |
| `apps/web` | Интерфейс диспетчера, серверное API и доменная логика | React 19, Vinext, Vite, TypeScript |
| `apps/web/db` | Схема и доступ к данным | Cloudflare D1, SQLite, Drizzle ORM |
| `services/optimizer` | Решение задач распределения и маршрутизации | Python, OR-Tools, PyVRP |
| `apps/android` | Мобильный клиент исполнителя | Kotlin, Jetpack Compose, Material 3 |
| `packages/provider-contracts` | Общие контракты провайдеров маршрутизации и планирования | TypeScript |
| `algorithm-research` | Датасеты, benchmark и результаты исследования алгоритмов | Python, JSON, CSV |

Web-приложение подготавливает предметные ограничения и дорожные матрицы, передаёт задачу выбранному оптимизатору и независимо проверяет результат перед сохранением черновика. Сервис оптимизации не имеет прямого доступа к базе данных, адресам или ключам карт.

## Быстрый локальный запуск

Установите JavaScript- и Python-зависимости из корня репозитория:

```powershell
corepack enable
pnpm install --frozen-lockfile

python -m venv algorithm-research/benchmark/.venv
./algorithm-research/benchmark/.venv/Scripts/python.exe -m pip install -r services/optimizer/requirements.txt
```

Создайте локальную конфигурацию:

```powershell
Copy-Item apps/web/.env.example apps/web/.dev.vars
```

В `apps/web/.dev.vars` задайте собственные реквизиты начального администратора, ключи используемых картографических API и непустой `OPTIMIZER_SERVICE_TOKEN`. Файл локальной конфигурации исключён из Git; секреты нельзя добавлять в репозиторий.

Запустите web-приложение и оптимизатор:

```powershell
./start-server.cmd
```

После успешного запуска:

- приложение: <http://127.0.0.1:3000>;
- health-check оптимизатора: <http://127.0.0.1:8765/health>;
- журналы процессов: `.tmp/local-runtime/`.

Скрипт не перезапускает уже занятые локальные порты. Если Node.js установлен нестандартно, полный путь можно передать через `MARSH_NODE_PATH`.

При первом запуске откройте приложение и войдите под реквизитами `AUTH_BOOTSTRAP_*` из `.dev.vars`. Первый авторизованный запрос к предметным данным создаст таблицы и применит зарегистрированные SQL-миграции. Затем проверьте страницу планирования, карту и запуск расчета; для карты должны быть заполнены оба ключа 2GIS.

### Ручной запуск

Для раздельной диагностики запустите сервисы в двух терминалах. Значение токена должно совпадать со значением в `.dev.vars`:

```powershell
$env:OPTIMIZER_SERVICE_TOKEN = '<локальный-секрет>'
./algorithm-research/benchmark/.venv/Scripts/python.exe services/optimizer/server.py --host 127.0.0.1 --port 8765
```

```powershell
pnpm web:dev
```

## Конфигурация

Основные переменные перечислены в `apps/web/.env.example`:

| Переменная | Назначение |
| --- | --- |
| `AUTH_BOOTSTRAP_*` | Начальная локальная учётная запись администратора |
| `TWO_GIS_API_KEY` | Серверные API геокодирования, матриц и маршрутов 2ГИС |
| `TWO_GIS_MAPGL_KEY` | Ограниченный по домену ключ карты 2ГИС |
| `OSM_TILE_URL` | Необязательный адрес растровых тайлов OpenStreetMap |
| `OSRM_BASE_URL` | Необязательный собственный автомобильный сервер OSRM |
| `OPTIMIZER_SERVICE_URL` | Серверный адрес Python-сервиса оптимизации |
| `OPTIMIZER_SERVICE_TOKEN` | Общий секрет web-приложения и оптимизатора |
| `PLANNING_DEPOT_LAT/LON` | Резервная координата стартовой точки планирования |

Пустой `OSRM_BASE_URL` включает публичный демонстрационный сервер OSRM. У него нет производственного SLA, поэтому для постоянной или интенсивной эксплуатации нужен собственный экземпляр.

## Миграции базы данных

Предметная база работает на D1/SQLite. SQL-миграции находятся в `apps/web/drizzle`, а примененные версии регистрируются в таблице `domain_schema_migrations`.

При обычном запуске отдельная команда миграции не нужна: приложение последовательно применяет еще не выполненные зарегистрированные миграции при первом обращении авторизованного пользователя к предметным данным. Локально состояние хранится в `apps/web/.wrangler/state/v3`, в Docker — в именованном томе `web-state`.

### Изменение схемы

1. Измените `apps/web/db/schema.ts`.
2. Сгенерируйте SQL:

   ```powershell
   pnpm --filter @mmi/web db:generate
   ```

3. Проверьте новый файл в `apps/web/drizzle`. Удаление таблиц, переименование колонок и преобразование данных требуют отдельной ручной проверки.
4. Импортируйте миграцию и зарегистрируйте ее в последовательности `initializeDomain` в `apps/web/db/domain-storage.ts`. Один только SQL-файл автоматически не подключается.
5. Запустите проверки:

   ```powershell
   pnpm check
   pnpm test
   pnpm web:build
   ```

6. Проверьте миграцию на копии данных или чистом локальном состоянии. Перед обновлением общего стенда обязательно сделайте резервную копию.

Не изменяйте уже выпущенную миграцию: каждое следующее изменение схемы оформляется новым SQL-файлом.

### Служебные миграции старых локальных баз

Эти команды нужны только для локальных состояний, созданных до перехода на текущую схему. Сначала остановите web-процесс и скопируйте `apps/web/.wrangler/state/v3` в безопасное место.

```powershell
pnpm --filter @mmi/web db:paused:check
pnpm --filter @mmi/web db:paused:apply

pnpm --filter @mmi/web db:guids:check
pnpm --filter @mmi/web db:guids:apply
```

Каждую пару сначала запускайте в режиме `check` и только после проверки отчета — в режиме `apply`. На новой установке эти команды не требуются.

### Тестовый набор данных

Скрипт перехода заменяет локальные предметные данные подготовленным набором `beeline-app-v1`, сохраняя пользователей и сессии. На время операции web-приложение должно быть остановлено.

```powershell
# Репетиция без изменения рабочей базы
node apps/web/scripts/local-dataset-transition.mjs

# Импорт после проверки отчета
node apps/web/scripts/local-dataset-transition.mjs --apply
```

Перед записью скрипт создает резервную копию в `apps/web/.tmp/dataset-transition`. Это локальный инструмент: не запускайте его напрямую на работающей production-базе.

```powershell
# Проверка типов всего TypeScript-кода
pnpm check

# Сборка общих контрактов
pnpm build

# Производственная сборка web-приложения
pnpm web:build

# Основной набор тестов контрактов и планирования
pnpm test

# Полный последовательный QA-набор
pnpm qa
```

Расширенный QA с браузерными и Android-проверками:

```powershell
pnpm qa --browser --android
```

Web backend и frontend можно полностью проверить в изолированном Linux-образе. QA-stage содержит Python-решатели и собственный headless Chromium, но не входит в production-образ:

```powershell
docker build --target qa --tag marsh-web-qa --file apps/web/Dockerfile .
docker run --rm marsh-web-qa
```

Полный QA требует настроенного Python-окружения, а расширенный запуск — поддерживаемого браузера, JDK и Android SDK. Подробности, ограничения изолированных тестов и расположение отчётов приведены в [документации по тестированию](docs/TESTING.md).

## Docker

Compose собирает production bundle web-приложения, запускает его в локальном Cloudflare runtime и подключает отдельный контейнер оптимизатора. Состояние эмуляторов D1 и R2 хранится в именованном томе `web-state`.

Подготовьте конфигурацию и замените значения-заглушки:

```powershell
Copy-Item .env.example .env
```

Проверьте конфигурацию, соберите образы и запустите сервисы:

```powershell
docker compose config
docker compose build
docker compose up -d
docker compose ps
```

По умолчанию сервисы доступны только через loopback:

- приложение: <http://127.0.0.1:3000>;
- оптимизатор: <http://127.0.0.1:8765/health>.

Проверить health endpoints и посмотреть журналы:

```powershell
Invoke-RestMethod http://127.0.0.1:3000/api/mobile/v1/health
Invoke-RestMethod http://127.0.0.1:8765/health
docker compose logs -f
```

Остановить стек без удаления данных:

```powershell
docker compose down
```

Команда `docker compose down --volumes` дополнительно удалит локальные D1/R2-данные. Используйте её только когда требуется полностью чистый запуск.

Без дополнительного профиля Compose предназначен для локального и стендового запуска собранного Worker через workerd. Для публичной эксплуатации используйте описанный ниже TLS reverse proxy, производственные секреты и резервное копирование; D1/R2 при этом продолжают работать локально в Docker volume.

### Развёртывание на одном сервере

Production-профиль запускает Caddy перед web-контейнером. Оптимизатор и служебный порт web-приложения остаются привязаны к loopback, а наружу публикуются только HTTP/HTTPS. D1, R2 и состояние Caddy сохраняются в именованных Docker volumes.

До настройки DNS задайте публичный IP с явной схемой HTTP:

```dotenv
APP_DOMAIN=http://203.0.113.10
```

После создания DNS-записи `A` замените значение на домен в ASCII/Punycode без схемы. Для `маршплан.рф`:

```dotenv
APP_DOMAIN=xn--80aa6acijg8d.xn--p1ai
```

Caddy автоматически запросит сертификат и включит HTTPS, когда DNS указывает на сервер и входящие TCP-порты 80/443 доступны. UDP 443 используется для HTTP/3.

Запуск production-профиля:

```bash
cp .env.example .env
chmod 600 .env
# Замените пароли, токен optimizer, APP_DOMAIN и необходимые ключи API.
docker compose --profile proxy config --quiet
docker compose --profile proxy up -d --build --wait
docker compose --profile proxy ps
```

Для локального ежедневного backup D1/R2 установите подготовленные systemd units:

```bash
chmod 750 deploy/backup.sh
cp deploy/marsh-backup.service deploy/marsh-backup.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now marsh-backup.timer
```

Архивы создаются в `/var/backups/marsh`, хранятся 14 дней и доступны только root. Во время снятия согласованной копии web-контейнер кратковременно останавливается. Копии на том же сервере не защищают от отказа диска, поэтому для production их нужно дополнительно вывозить во внешнее хранилище.

Публичный демонстрационный OSRM не имеет производственного SLA. Для автономной эксплуатации укажите локальные `OSRM_BASE_URL`, `OSRM_WALKING_BASE_URL` и `OSRM_CYCLING_BASE_URL` либо разверните соответствующие профили маршрутизации на этом же сервере.

## Обновление развернутого стенда

Перед обновлением создайте резервную копию. На сервере с установленными systemd units:

```bash
cd /opt/marsh
sudo systemctl start marsh-backup.service
sudo systemctl show marsh-backup.service -p Result -p ExecMainStatus
```

Продолжайте только при `Result=success` и `ExecMainStatus=0`. Архив состояния должен появиться в `/var/backups/marsh`.

```bash
cd /opt/marsh
git pull --ff-only
docker compose --profile proxy up -d --build --wait
docker compose --profile proxy ps
docker compose --profile proxy logs --since=10m web optimizer caddy
```

Новые зарегистрированные миграции применятся при первом авторизованном запросе к предметным данным. После обновления войдите через web-интерфейс и проверьте планирование, карту и запуск расчета. Успешный healthcheck сам по себе не подтверждает применение предметных миграций.

Если миграция завершилась ошибкой, не удаляйте Docker volume и не правьте базу вручную. Сохраните журналы, остановите обновленный web-сервис и восстановите последнюю копию `web-state-*.tar.gz` в отдельный чистый том либо верните предыдущую версию приложения.

## Диагностика запуска

- `node` или `pnpm` не найдены: установите Node.js нужной версии, выполните `corepack enable` и повторите `pnpm install --frozen-lockfile`.
- Web не стартует: проверьте порт `3000` и журнал `.tmp/local-runtime/web-error.log`.
- Optimizer недоступен: проверьте порт `8765`, Python-окружение и `.tmp/local-runtime/optimizer-error.log`.
- Карта не загружается: проверьте оба ключа 2GIS в `.dev.vars` или `.env`, затем перезапустите web-процесс.
- Расчет возвращает `401`: `OPTIMIZER_SERVICE_TOKEN` должен совпадать у web-приложения и optimizer.
- Контейнер не проходит healthcheck: выполните `docker compose ps` и `docker compose logs --tail=200 web optimizer`.
- Старая база сообщает о миграциях `0009/0010`: не удаляйте состояние; сделайте копию и сначала выполните служебные миграции из раздела выше.

## Безопасность локальной среды

- не коммитьте `.env`, `.dev.vars`, токены, ключи API и локальные базы;
- не публикуйте Python-сервис напрямую в интернет: вне loopback используйте токен и HTTPS reverse proxy;
- не запускайте device-тесты Android на пользовательском устройстве — они могут очищать локальные данные приложения;
- миграционные и demo-скрипты могут менять локальное состояние D1, поэтому перед запуском проверяйте их назначение.
