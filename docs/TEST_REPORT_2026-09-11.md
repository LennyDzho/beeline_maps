## Дефект 1 — редактирование пользователя чужого юрлица

Приоритет исправления: высокий, граница доступа к данным. Сценарий `ADM-02` в [application-api.test.mjs](../apps/web/tests/application-api.test.mjs).

Воспроизведение в изолированной БД:

1. Создать пользователя только в `ORG-002`.
2. Использовать допустимый произвольный ID строки его членства, как при внешнем заведении/импорте данных.
3. Оставить проверяемому администратору доступ только к `ORG-001`.
4. Через `PUT /api/admin/users` передать ID чужого пользователя и другое имя.

Ожидается 403/404 без изменений. **Фактически HTTP 200**: обработчик принимает изменение.

Причина: в [api/admin/users/route.ts](../apps/web/app/api/admin/users/route.ts), начиная со строки 44, существование пользователя проверяется глобально по ID. Членство целевого пользователя в выбранном юрлице не проверяется; затем выполняется глобальный `UPDATE users` и добавление членства. При некоторых автоматически сформированных ID операция может вместо этого упереться в конфликт первичного ключа — это не корректная проверка прав.

Критерий исправления: сервер проверяет доступ к **целевому пользователю**, а не только право текущего администратора; чужие данные и членство не меняются. Политику редактирования общих пользователей нескольких юрлиц нужно определить явно. Тест должен пройти без ослабления ожидания 403/404.

## Дефект 2 — публикация устаревшего черновика

Приоритет исправления: высокий, риск потери правок диспетчера. Сценарий `PLAN-04`.

Воспроизведение:

1. Рассчитать черновик на 20.08.2026.
2. У заявки из маршрута изменить начало/конец на 16:00–17:00, сохранив статус `assigned`. Revision увеличится.
3. Опубликовать ранее рассчитанный черновик.

Ожидается 409 и предложение пересчёта. **Фактически HTTP 200, `status: published`**. Старый черновик допускается к применению и может перезаписать новое время.

Причина: [planning-service.ts](../apps/web/app/lib/server/planning/planning-service.ts), строки 135–137, проверяет организацию и статус заявки, но не изменение её revision/времени после расчёта. Обновление назначений и времени при публикации выполняется дальше по старым остановкам маршрута.

Критерий исправления: сохранить исходные версии/значимые параметры расчёта, проверить актуальность при публикации и защитить запись от конкурентного изменения. Изменение времени, адреса, исполнителя, требований либо графика должно иметь явную политику инвалидирования черновика.

## Что не проверено

- Реальные ключи, лимиты, доступность, пробки и геометрия 2ГИС/OSRM: использованы фиксированные HTTP-ответы.
- Сквозной запуск на пользовательском/физическом Android, камера и офлайн-очередь после завершения процесса. Существующие device-тесты скомпилированы, **не запущены**, поскольку часть из них очищает настройки и меняет backend.
- Полный цикл загрузки фото/видео в R2: проверены сигнатуры/потоки и требования мобильных команд, но не реальное хранилище.
- Нагрузки 100–1000 заявок, сбои в середине большой публикации, полный набор параллельных гонок, восстановление из backup, полный аудит безопасности и доступности.
