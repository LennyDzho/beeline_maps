# Проблемы и приостановленные заявки

Веб-диспетчерская и Android «Марш!» 0.3.1 используют общий статус `paused` — «Приостановлена».

## Поведение

- Сообщение о проблеме доступно из назначенной заявки, «В пути» или «В работе». Причина и описание обязательны.
- Сервер одной транзакцией сохраняет запись `mobile_issues`, переводит заявку в `paused`, записывает переход в `work_order_status_history` и событие аудита. Время — серверный UTC; диспетчерский журнал показывает дату и время с секундами в МСК.
- Повтор команды с тем же `operationId` не создаёт второе сообщение. Изменённая версия заявки даёт конфликт без частичного сохранения.
- Приостановленная заявка не считается активным выполнением. Исполнитель может начать другую задачу или закончить смену.
- «Продолжить» переводит только `paused → in_progress`. Нужна открытая смена, действующее назначение и отсутствие другой заявки «В пути»/«В работе». Завершить приостановленную заявку без продолжения нельзя.
- Черновики отчёта и материалы не удаляются при приостановке. Каждая повторная приостановка после продолжения добавляет отдельное сообщение; старые записи сохраняются.
- В Android прежние приостановленные заявки остаются доступны при выборе следующего дня. Следующая обычная задача имеет приоритет, приостановленные показаны в конце расписания.
- В диспетчерской: «Заявки → Журнал проблем», журнал внутри карточки, фильтр «Приостановлены», жёлтая отметка в конце списка задач исполнителя — в том числе если для него нет рассчитанного маршрута. Списки обновляются каждые 15 секунд и при возвращении в окно.
- Оптимизация выбирает только `new`/`assigned`; приостановленные заявки не перераспределяются. Старый черновик с уже начатой/приостановленной задачей требует перерасчёта перед публикацией.
- При отсутствии связи Android сохраняет команду в очереди. Статус считается подтверждённым только после ответа сервера; до этого показано ожидание синхронизации.

Исторические сообщения отображаются с уже сохранённым временем. Старые сообщения сами по себе не переводят заявки в паузу задним числом.

## Зависшая проблема при конфликте версии

В Android 0.3.1: «Сегодня → Разобрать очередь отправки» (либо «Профиль → Связь») → «Повторить отправку проблемы». Диалог показывает актуальные статус, адрес, время заявки и сохранённый текст. Подтверждение — «Отправить и приостановить».

- API различает `409 revision_conflict` и остальные конфликты. Проверка версии и транзакционные ограничения остаются обязательными.
- При таком конфликте Android перестаёт автоматически отправлять отвергнутую проблему, но продолжает получать расписание. Ничего не удаляется; новый идентификатор операции создаётся только после подтверждения.
- Перед повторной отправкой воспроизводится исходная команда с прежним идентификатором: потерянное подтверждение не должно создать дубль. Затем повторно загружается заявка и сравнивается с подтверждёнными пользователем данными. При новой правке требуется новое подтверждение.
- Подмена версии для команд завершения работы, смены или при ошибках прав не выполняется. При закрытии, приостановке или снятии назначения повторная отправка проблемы не предлагается.
- Обновлённая очередь сохраняется на диск до замены в памяти; после сетевого обрыва повтор используется с тем же новым идентификатором. Исходный текст сохраняется.
- Начальное наполнение больше не обновляет существующие заявки, адреса объектов и параметры исполнителей при запуске. Следовательно, повторный запуск не увеличивает `revision` и не возвращает адреса к демонстрационным значениям. Одноразовые исправления данных не выполняются в стартовом наполнении.

Обновление APK устанавливается поверх прежнего (`adb install -r`), без удаления приложения и очистки его данных. Дополнительная миграция базы для 0.3.1 не нужна.

## Безопасное обновление локальной базы

Миграция `0010_nifty_stature` расширяет CHECK статуса. SQLite требует пересоздания таблицы, поэтому применять её к существующей локальной базе нужно **только офлайн**, через `apps/web/scripts/migrate-paused-local.mjs`:

1. Без аргументов скрипт делает согласованную резервную копию SQLite (включая WAL) и проверяет миграцию на отдельной копии. Рабочая база не меняется.
2. Остановить локальный сервер.
3. Запустить с `--apply`. Скрипт откажется работать при доступном порте 3000; создаст новую резервную копию, проверит копию и обновит рабочую базу в транзакции.
4. После копирования таблицы сравнивается содержимое **всех таблиц**, проверяются внешние ключи и целостность. При несовпадении — откат. Триггер увеличения `revision` восстановлен в миграции.
5. Запустить сервер. Резервные копии находятся в игнорируемой папке `apps/web/.tmp/paused-migration/`.

Не запускать эту реконструкцию из HTTP-обработчика. Для будущего развёртывания в облачном D1 нужен отдельный согласованный процесс миграции с учётом запрета отключения FK: простая замена `foreign_keys=OFF` на `defer_foreign_keys` не защищает дочерние записи от каскадного удаления. Публикация в рамках этой доработки не выполняется.

## Проверки

`pnpm --dir apps/web test:workflow` — реальные серверные функции с SQLite в памяти, без тестовых записей в пользовательской базе. Проверяются пауза, продолжение, повторная доставка, конфликт версии, права, рабочая смена, журнал, переход между днями и сортировка карточек. Отдельный тест повторяет SQL стартового наполнения и проверяет неизменность существующих заявок, адресов и параметров исполнителей.

`apps/android/build.ps1 -CompileDeviceTests` — APK, модульные тесты, lint и компиляция инструментальных тестов. Автоматическое выполнение тестов на пользовательском эмуляторе и удаление его данных не требуются.
