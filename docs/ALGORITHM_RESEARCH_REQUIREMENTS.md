# Требования к алгоритму распределения заявок и планирования маршрутов

**Назначение:** постановка для исследования и выбора open-source алгоритма или решателя для приложения «Марш!». Документ описывает требуемое поведение независимо от конкретной библиотеки и картографического сервиса.

**Редакция:** 17 сентября 2026 года. Основание — ТЗ Билайн Бизнес, ответы встречи и последующие решения владельца проекта D-001–D-033. Это требования к целевому решению; наличие пункта здесь не означает, что он уже реализован. Подбор библиотек и проверка их возможностей — следующий этап исследования.

Дополнение вне исходного ТЗ от 17.09.2026: [D-030–D-033](ADDITIONAL_PRODUCT_REQUIREMENTS.md) вводят часовой пояс каждого исполнителя, оборудование работ/заявок, уведомления диспетчеру и иерархию ВК → набор HD. Ниже обновлены временная модель и проверка компетенций; сообщения и отчёт оборудования относятся к интеграции, а не к внутреннему устройству решателя.

## 1. Краткая постановка

Нужно распределить заявки одного рабочего дня между исполнителями, выбрать порядок посещения и плановое время каждой работы. Исполнители различаются компетенциями ВК → HD, часовым поясом, способом перемещения, сменой и стартовой точкой. Заявки имеют адрес, набор требуемых HD-работ внутри ВК, длительность, оборудование, временное окно начала и иногда ограничение по транспорту.

**Основные цели:**

1. Максимизировать количество заявок, которые можно выполнить с соблюдением обязательных ограничений.
2. При одинаковом количестве выполненных заявок минимизировать число задействованных исполнителей.
3. Измерять дорожный пробег каждого исполнителя и всего плана; сокращение суммарного пробега использовать как дополнительный критерий.

**Особый сценарий — аварии:** заявка срочная, окно допускает выполнение в течение суток, но выполнить её нужно как можно быстрее. Возможность поставить аварию вечером не означает, что это хороший результат, если есть допустимое раннее назначение. Нужны приоритет и поиск ранней вставки, а не только проверка широкого временного окна.

При изменении ситуации пересчитывается оставшаяся часть дня. Уже начатые работы и поездки защищены. Изменения назначений и сроков должны быть объяснимы короткими фактическими причинами.

Отдельный последовательный базовый алгоритм из §2.3 первоначального ТЗ **не требуется** по ответу владельца. Сравнение кандидатов при исследовании и сравнение плана до/после перепланирования сохраняются.

## 2. Область задачи и объём данных

| Параметр | Требование |
|---|---|
| Подразделения | Восток, Юго-восток, Югоцентр; независимые пулы заявок и исполнителей |
| Между подразделениями | Назначения запрещены, даже если другой исполнитель географически ближе |
| Общий запуск | Рассчитывает все доступные подразделения на выбранную дату, собирает общий план и метрики |
| Горизонт | Один рабочий день; перенос невместившихся заявок на следующий день не является способом решения исходной задачи |
| Исполнитель | Одна карточка инженера; название «бригада» не означает несколько человек |
| Начальный справочник | 12 / 12 / 11 исполнителей, всего 35; одинаковое название в двух подразделениях — разные исполнители |
| Сырой набор | 205 строк заявок; пустые строки и строки офисов заявками не являются |
| Рабочий набор | 204 заявки после исключения подтверждённого дубля: 203 новые и 1 исторически выполненная |
| Первичный расчёт | 203 новые: 66 / 81 / 56 по подразделениям; выполненная не назначается повторно |
| Расширение | Число исполнителей и заявок — входные данные, а не зашитые пределы. Проверять масштабирование отдельно |

Количество 35 — размер исходного справочника, а не требование использовать всех. Решатель не должен создавать дополнительных исполнителей самостоятельно. При нехватке ресурсов он может оценить потребность в них, но такой сценарий должен быть явно отделён от решения на данном составе.

Синтетические и контрольные CSV описывают связанные строки, а не два независимых набора работ. Для текущих файлов применяется проверенное позиционное сопоставление с проверкой общих полей, затем исключается дубль. Историческое контрольное распределение не является оптимальным эталоном, совпадение назначений с ним не требуется.

## 3. Входная модель

Названия полей ниже логические, не обязательная схема API. Ввод/показ времени выполняется в явно указанном часовом регионе. Внутри расчёта моменты приводятся к единой шкале и точности, например UTC, с сохранением исходного локального времени и пояса; одинаковая запись «10:00» в разных GMT-регионах не означает один момент.

### 3.1. Исполнитель

| Поле | Смысл |
|---|---|
| `workerId`, `divisionId` | Стабильные внутренние идентификаторы исполнителя и подразделения |
| `supportedHdTypesByBk` | Разрешённые HD-работы по категориям ВК, выбранные галочками; требуются все HD заявки |
| `timeZone` | Часовой регион GMT±, влияет на интерпретацию смен и расписания |
| `transportMode` | Один режим: автомобиль, пешком, велосипед, общественный транспорт |
| `shiftStart`, `shiftEnd` | Разрешённое рабочее время; значения задаются сценарием, а не выводятся из CSV |
| `ownStartLocation` | Собственная стартовая точка, если задана |
| `divisionStartLocation` | Адрес подразделения для старта по умолчанию |
| `availability` | Доступен ли исполнитель; при перепланировании — момент следующей доступности |
| `currentLocation` | Положение на момент события либо явно обозначенная модельная оценка |
| `fixedActivities` | Уже начатая/защищённая часть дня, которую нельзя свободно переставлять |

Эффективный старт: собственная точка, если задана, иначе офис подразделения. Ошибка геокодирования собственного адреса не означает отсутствие адреса и не должна незаметно переключать старт на офис.

После последней работы **не требуется возврат на базу**. Дорога от старта к первой заявке учитывается. В перепланировании старт оставшейся части — актуальное положение и доступность, а не утренний офис.

### 3.2. Заявка

| Поле | Смысл |
|---|---|
| `jobId`, `divisionId` | Внутренний ID заявки и её подразделение |
| `location`, `fullAddress` | Координаты здания и полный адрес для диспетчера/исполнителя |
| `workType`, `sourceBK`, `sourceHD` | Нормализованный вид работы и исходные категории |
| `bkType`, `requiredHdTypes` | Одна категория ВК (BK в CSV) и набор выбранных HD-работ; составной тип даёт несколько элементов |
| `timeZone` | Часовой контекст окна/даты заявки до назначения; не выводится заново при каждом переносе |
| `requiredEquipment` | Перечень из выбранных видов работ с источником/версией; количества и способы агрегации задаются отдельно |
| `requiredTransportMode` | Необязательное требование; отсутствие означает любой допустимый режим |
| `windowStart`, `windowEnd` | Границы разрешённого **начала работы** |
| `serviceDuration` | Техническая работа и оформление документов, без дорожного времени |
| `priority`, `isEmergency` | Обычная/срочная и признак аварии; передаются явно после нормализации |
| `releaseTime` | Когда заявка становится известна и доступна для назначения; важно для события в течение дня |
| `status` | Текущее состояние нашего приложения, а не исторический статус CSV |
| `previousAssignment`, `previousSchedule` | Предыдущий исполнитель и плановые сроки, если они были |
| `assignmentHistory` | Нужна для отличия первого назначения от повторного после снятия |
| `protection` | Подтверждение клиентом и прочие действующие ограничения автоматического изменения |
| `source` | Файл, строка, внешние ID, исходное окно и источник норматива для воспроизводимости |

Дополнительное требование D-033 уточняет модель компетенций: ВК — родительский фильтр, HD — множественный выбор. У заявки одна ВК и набор требуемых HD; у исполнителя разрешённые HD по ВК. Проверяется включение всего набора: `requiredHdTypes(job) ⊆ supportedHdTypes(worker, job.bkType)`. Совпадения одной крупной категории недостаточно. Три группы навыков исходного ТЗ могут остаться совместимым представлением, но не заменяют подробную проверку.

«Заказ подключения» и «Заявка на подключение» нормализуются в один тип. «Заказ подключения/Дозаказ оборудования» даёт два HD в одной заявке/одном визите. Не раздваивать назначение и не считать одну такую заявку двумя выполненными в целевой функции. Правило времени нескольких работ должно быть отдельным, а не неявной суммой исходных BK-нормативов.

Каждая строка рабочего набора — отдельный визит, включая «Информацию» и «Мониторинг». Выполнение одной аварии не закрывает другие заявки автоматически. Разделение одной работы между несколькими исполнителями, прерывание работы и параллельное обслуживание одним человеком в данном кейсе не предусмотрены.

Квартира, подъезд и домофон относятся к карточке и доступу к объекту. Для геокодирования используется адрес здания. Совпадение адресов не является достаточным основанием склеить заявки.

## 4. Временная модель: окно, дорога, ожидание, работа

### Уточнение оборудования от 19 сентября — D-034

До выезда бригада получает в офисе комплект для всего опубликованного дневного плана; будущая потребность не ограничивает начальную оптимизацию остатками у бригады. После выезда полученный комплект фиксируется отдельно. Для автоматического назначения требуется `requiredEquipment(job) ⊆ receivedEquipment(brigade, day)` по всем HD. Отсутствие сведений о выданном комплекте не означает, что у выехавшей бригады есть любое оборудование.

Перепланирование не пополняет комплект за счёт новых заявок. Изменение выдачи или выезд во время расчёта делают снимок устаревшим. Ручное назначение с недостающим оборудованием допускается, но в плане требуется красное предупреждение с перечнем. Количественный расход уточняется отдельно; реализованное ограничение относится к наличию видов оборудования. Исследовательскую кампанию это уточнение автоматически не возобновляет.

### 4.1. Обязательная семантика окна

Для обычной заявки `i`:

```text
arrival_i = departure_previous + travelTime(previous, i, worker, departure_previous)
start_i >= max(arrival_i, windowStart_i, releaseTime_i)
start_i <= windowEnd_i
finish_i = start_i + serviceDuration_i
```

Можно приехать раньше и ждать. Начать до открытия окна нельзя. Завершение работы может быть позже конца клиентского окна, но должно укладываться в смену исполнителя. Последовательность должна оставаться допустимой для всех следующих заявок.

Для расчёта самого раннего начала используется равенство `start_i = max(...)`. Решатель может сдвигать начало позже в пределах допустимости, если это обосновано планом; для срочной аварии лишнее ожидание ухудшает качество.

Пример: окно 10:00–12:00, начало 11:50, работа 40 минут, конец смены 18:00 — допустимо. Работа завершится в 12:30. Начало в 12:01 — нарушение, даже если оно даёт более короткий маршрут.

Границы обычного окна включаются в принятой модели: начало ровно в `windowEnd` допустимо. Это правило реализации должно быть одинаковым у всех исследуемых кандидатов. Все даты текущего набора относятся к Europe/Moscow (GMT+03:00). В расширенной модели D-030 у исполнителей могут быть разные пояса: смены и окна нормализуются по своим явно заданным часовым контекстам. Смена пояса не сдвигает сама по себе согласованный абсолютный момент визита; изменение момента требует причины по D-028.

### 4.2. Дорога не входит повторно в длительность работы

В полученном файле «Нормативы.xlsx», лист «Лист1»!A1:E5, базовый норматив уже складывается из дороги, технических работ и документов:

| Категория источника | Дорога, мин | Работы, мин | Документы, мин | Сумма источника, мин | Обслуживание без дороги, мин |
|---|---:|---:|---:|---:|---:|
| Подключение клиентов Базовая | 20 | 60 | 10 | 90 | 70 |
| Аварий на ТКД | 20 | 80 | 0 | 100 | 80 |
| Дозаказ оборудования | 20 | 10 | 10 | 40 | 20 |
| Локальная заявка/ремонт у клиента | 20 | 30 | 0 | 50 | 30 |

**Рабочая модель для исследования:** брать 70/80/20/30 минут обслуживания, заменять фиксированные 20 минут дороги временем конкретного перехода из картографического сервиса. Не складывать полную сумму источника и дорожную матрицу. При дороге 35 минут подключение занимает 35 + 70 = 105 минут без ожидания, а не 125.

Применение четырёх строк ко всем BK/HD и состав дорожных 20 минут остаются уточнением Q-044. Для эксперимента зафиксировать явное соответствие: BK «Подключение» → 70, «Глобальная проблема» → 80, «Дозаказ» → 20, «Локальная заявка» → 30. Это настройка исследовательского набора, не отсутствующая колонка исходного Excel. Признак срочности должен быть отдельным правилом нормализации: не выводить его автоматически из выбранной длительности.

Для нескольких HD в одной заявке длительность — отдельный параметр, подготовленный предметным слоем по явному правилу. Сложение 70 минут подключения и 20 минут дозаказа не принимается автоматически: возможны общие документы/операции. Это вопрос реализации D-033. Дорогу к одному визиту всегда учитывать один раз независимо от числа выбранных работ.

Ранее вычисленные 120/1087 минут — средняя ширина клиентских окон, не трудоёмкость. Для исследования реалистичной вместимости маршрутов эти значения не использовать. Не вводить дополнительный запас 20 минут поверх маршрута без отдельного обоснования.

### 4.3. Матрицы и география

- Картографический слой возвращает дорожное время, расстояния и геометрию; решатель занимается распределением и ограничениями.
- Нужны внешние матрицы, зависящие от режима перемещения, а при необходимости — от исполнителя и времени отправления.
- Матрица может быть направленной: путь A → B не обязан совпадать с B → A. Отсутствующий путь не заменять нулём.
- Расстояния по прямой не выдавать за дорожный пробег. Приближённая модель допустима только с явным описанием и едиными условиями сравнения.
- Для общественного транспорта учитывать его профиль либо явно обозначать используемое приближение. Пешая оценка времени не изменяет тип транспорта исполнителя при проверке совместимости.
- Статическая матрица на выбранное время — допустимое исследовательское допущение. Для нескольких временных срезов измерять влияние на качество отдельно. Нельзя сравнивать библиотеки на разных матрицах и приписывать разницу самому алгоритму.

## 5. Жёсткие ограничения допустимого автоматического плана

| ID | Ограничение | Что проверяет независимый валидатор |
|---|---|---|
| H01 | Заявка назначается не более одного раза | Нет повторов назначения и повторного учёта одного визита |
| H02 | Исполнитель и заявка одного подразделения | Совпадают `divisionId` |
| H03 | Исполнитель выполняет все выбранные HD заявки | Категория ВК допустима, весь `requiredHdTypes` включён в его компетенции этой ВК |
| H04 | Соблюдено требование транспорта заявки | Ограничение отсутствует либо режим совместим |
| H05 | Работа начинается внутри окна | Отдельно проверены начало, окно и время появления заявки |
| H06 | Работа, ожидание и необходимая дорога укладываются в смену | Нет выезда до допустимого начала смены и завершения после её конца |
| H07 | У исполнителя нет одновременных работ | Интервалы обслуживания не пересекаются |
| H08 | Между работами достаточно времени для дороги | `start_next >= finish_previous + travelTime` с учётом принятой модели |
| H09 | Старт маршрута корректен | Собственная точка/офис для первичного расчёта, актуальная точка при событии |
| H10 | Нельзя автоматически менять защищённую часть | Начатые работы, поездки и подтверждённые визиты обработаны по правилам раздела 8 |
| H11 | Событие не изменяет прошлое | Новые назначения и перемещения происходят не раньше `eventAt`/доступности |
| H12 | После выезда имеется всё требуемое оборудование | По D-034 проверяется полученный дневной комплект по всем HD; до выезда комплект формируется по плану. Количественные складские остатки не выдумываются |
| H13 | Часовые регионы учтены | Локальные смены, окна и события переводятся в реальные моменты; пояс браузера не меняет смысл времени |

План с нарушенными жёсткими ограничениями нельзя объявить лучшим за счёт штрафов в общей стоимости. Если решатель допускает мягкие нарушения, слой приложения должен отличать их от допустимого результата и не скрывать в метриках.

**Не добавлять неоговорённые ограничения:** максимум 12 заявок, максимум 6 часов дороги, обязательный возврат на базу, универсальную смену 09:00–18:00, одинаковый транспорт всех исполнителей. Лимиты применяются только как явно заданные параметры сценария.

Перечень оборудования каждого вида работ, его перенос в заявку и сводка по исполнителям теперь обязательны для расширенного продукта D-031. Отчёт агрегирует требования по выбранному плану, включая отдельную группу неназначенных; правила количеств и повторного использования задаются отдельно. Это данные и отчётность вокруг решателя, а не автоматически введённое ограничение складских остатков.

Перерывы, общий склад оборудования, передача устройств при встрече, многодневное планирование, несколько инженеров на одной заявке — возможное дальнейшее развитие продукта. Они не должны становиться обязательной частью минимального исследования без отдельного сценария. При выборе библиотеки полезно оценить расширяемость под эти требования.

## 6. Цели оптимизации и их измерение

### 6.1. Первичное распределение

Пусть `J` — очередь, допустимая к планированию на этом запуске, `y_i` — признак включения заявки `i` в допустимый маршрут, `u_k` — признак использования исполнителя `k`.

```text
served = sum(y_i)                      # допустимо запланированные заявки
unassigned = |J| - served
workersUsed = число уникальных k с хотя бы одной работой
distance = сумма расстояний реальных переходов всех маршрутов
```

Сначала обеспечить допустимость. Для обычного первичного плана применять последовательность целей:

```text
1. maximize served
2. при том же served: minimize workersUsed
3. при тех же served и workersUsed: minimize distance
```

Это лексикографический порядок: небольшая экономия километров не компенсирует потерю заявки или лишнего исполнителя. Если библиотека предлагает только взвешенную сумму, исследователь должен показать, как веса обеспечивают этот порядок на заявленном диапазоне входов; произвольные коэффициенты недостаточны.

«Выполнено» в функции цели означает **запланировано выполнимо**, не фактический статус выполнения. Исторически завершённую заявку нельзя добавлять в числитель новых назначений. Ошибки исходных данных показываются отдельно; запрещено скрыто удалять сложные заявки из знаменателя для улучшения процента.

При перепланировании фиксированная часть дня сохраняется. Показывать число людей во всём плане и, отдельно, новых привлечённых после события. Один исполнитель с несколькими участками маршрута считается один раз. Не считать «освобождённым на весь день» человека, уже выполнявшего фиксированные работы.

### 6.2. Приоритет аварий — отдельный фактор качества

Для каждой срочной аварии измерять:

```text
responseDelay_i = plannedStart_i - releaseTime_i
completionDelay_i = plannedFinish_i - releaseTime_i
```

Начало и завершение показывать отдельно. При одинаковой длительности раннее начало даёт раннее завершение. Широкое окно определяет допустимость, а задержка реакции — качество. Один большой штраф за неназначение аварии не обеспечивает раннего выезда, если после её назначения все часы суток имеют одинаковую стоимость.

**Согласованное обязательное поведение:** авария срочная, выполняется как можно раньше среди допустимых решений; могут пересматриваться ещё не начатые обычные работы. Простая сортировка аварий первыми без проверки итогового времени реакции недостаточна.

**Не определён численно компромисс:** насколько раннее устранение аварии может увеличивать число исполнителей или уменьшать общее покрытие. Например, аварию можно начать в 11:00 с дополнительным инженером либо в 16:00 текущим составом. Нельзя незаметно выбирать между этими вариантами произвольным весом.

Для исследования сравнить как минимум две явно подписанные политики, не объявляя их уже согласованными правилами продукта:

| Политика для эксперимента | Порядок после жёсткой допустимости | Что показывает |
|---|---|---|
| Приоритет быстрого реагирования | Общее покрытие → покрытие аварий → задержка реакции → число исполнителей → пробег | Стоимость раннего выполнения в дополнительных людях/километрах |
| Минимальный штат при данном покрытии | Общее покрытие → покрытие аварий → число исполнителей → задержка реакции → пробег | Задержку, возникающую при ограничении задействованного персонала |

Ситуацию, когда ради аварии теряются обычные заявки, показывать отдельным сценарием с изменением покрытия. Жёсткие окна остальных назначенных заявок нарушать нельзя. Правило допустимой потери покрытия, срок реакции и порядок нескольких конкурирующих аварий требуют отдельного выбора по результатам исследования. Не придумывать SLA «30 минут» или «2 часа» без исходного требования.

## 7. Планирование срочной аварии

### 7.1. Суточное окно

Аварии нормализуются как срочные с окном на календарные сутки выбранного дня в часовом регионе заявки/плана (D-030); для московского набора — Europe/Moscow / GMT+03:00. Правая граница дня исключает полночь следующего дня. Это не «24 часа с момента поступления»: такой вариант требует отдельного бизнес-правила.

Фактически поиск ограничен также временем появления аварии, текущим событием, сменой и доступностью исполнителя. Авария, появившаяся в 13:00, не может получить плановое начало в 10:00. Суточное окно не продлевает смену до полуночи и не увеличивает норматив работ.

Сохранять исходные поля окна из CSV для происхождения. Если исходная аварийная строка имела двухчасовой интервал, применение суточного окна должно быть явной нормализацией по решению владельца, а не потерей исходных данных.

### 7.2. Предложенная эвристика вставки

1. Зафиксировать время события, актуальный план, статусы и доступность. Отделить защищённую часть от свободной для изменения.
2. Отобрать исполнителей нужного подразделения, способных выполнить все выбранные HD-работы аварийной заявки: компетенции ВК/HD, транспорт, смена с правильным часовым контекстом, действующие ограничения.
3. Для каждого кандидата рассмотреть позиции до первого свободного визита, между визитами и после последнего. Учитывать переход от текущего/фиксированного положения.
4. Рассчитать раннее начало аварии, её завершение и путь к следующей работе. Проверить все последующие затронутые окна, поездки и конец смены. Геометрического «свободного промежутка» без этих проверок недостаточно.
5. При необходимости сдвигать, менять порядок или перераспределять ещё не начатые обычные работы. Это поиск нового допустимого плана, а не разрешение нарушать их окна.
6. Сравнить кандидатов по принятой политике срочности, покрытию и ресурсу; сформировать новый маршрут и список изменений.
7. Если локальная вставка не найдена, расширить поиск: перестановки и переносы между маршрутами, перерасчёт затронутого подразделения. Возможность повторно использовать предыдущий план как старт решения желательна.
8. Если в пределах бюджета поиска результат не найден, вернуть неназначенную аварию с честной причиной и статусом поиска. Не объявлять доказанную невозможность по одному неудачному проходу эвристики.

Эта последовательность описывает желаемое поведение; допустима другая стратегия с теми же ограничениями и качеством. Нужно проверить, умеет ли кандидат реагировать на широкое окно аварии, а не всегда ставит её в наименее загруженный поздний участок.

## 8. Перепланирование и защищённое состояние

| Состояние | Правило |
|---|---|
| `new`, `assigned` | Основной пул изменения, с учётом дополнительных защит |
| `en_route` | Поездка уже началась; автоматически не разворачивать и не переназначать |
| `in_progress`, `paused` | Не перераспределять автоматически; учитывать оставшуюся занятость/неопределённую доступность |
| `completed`, `confirmed`, `cancelled` | Не возвращать в очередь новых работ |
| Подтверждённый клиенту визит | Не менять автоматически без установленного подтверждения диспетчера о согласовании с клиентом |

Подтверждение визита клиентом — отдельная защита и не тождественно статусу `confirmed` завершённой работы. Для защищённого визита можно показать предложение изменения отдельно; до требуемого согласования действующим остаётся прежний план. Такой кандидат не считать автоматически применимым.

Простого исключения начатой заявки из очереди недостаточно: её исполнитель остаётся занят. Для остатка дня нужны положение, момент освобождения и дорога от него. Если конец приостановки неизвестен, не считать человека мгновенно свободным; использовать явную оценку сценария либо сообщать о недостающей доступности.

Поддержать события: новая срочная авария; отмена заявки; недоступность исполнителя; ручное изменение назначения или сроков. Не каждое событие требует полностью пересчитать все подразделения, но результат общего запуска должен быть согласованным.

Решатель возвращает **черновик**. Он не изменяет рабочую базу сам. Приложение проверяет актуальность версий всех участвующих подразделений и публикует общий план атомарно. При конкурентной правке публикация отклоняется; старое решение не должно затереть ручное изменение. Это обязанность интеграции, не требование встроенной авторизации или транзакций к библиотеке оптимизации.

## 9. Результат и краткие объяснения

### 9.1. Обязательные данные результата

- Для исполнителя: упорядоченный маршрут, заявки, плановое прибытие/начало/окончание, ожидание, время дороги, расстояние переходов и всего маршрута.
- Для заявки: исполнитель либо «не назначена»; исходное окно сохраняется отдельно от плановых сроков.
- Для плана: покрытие, неназначенные, уникальные исполнители, километры по каждому и сумма; отдельно срочные, их время реакции и завершения.
- Для перепланирования: назначения, порядок, сроки и маршруты до/после; новые привлечённые исполнители; изменившиеся и снятые работы.
- Технически: статус решения, достигнутый лимит времени, версия входных данных, матриц, нормативов, алгоритма и параметров, начальное зерно случайности при его использовании.

### 9.2. Правила объяснений

Первое успешное получение исполнителя за всю историю заявки не требует описания выбора. Повторное назначение после снятия не считается первым. Неопубликованный черновик сам по себе не создаёт историю свершившихся назначений.

Краткая причина требуется для переноса, перераспределения, снятия назначения и последующих изменений сроков. Причина нужна и при прежнем исполнителе, и при ручной правке, и у каждой заявки, сдвинутой по цепочке из-за аварии. Пример: «Начало 14:00 → 14:30: у исполнителя появилась срочная авария».

У прежнего исполнителя показывать снятие, у нового — перенос от прежнего; причина связана с одним изменением. Снятие отображается даже при пустом новом маршруте прежнего исполнителя и не считается активной остановкой. Если нового назначения нет, заявка появляется среди неназначенных с причиной.

Для неназначенных причины нужны всегда: нет компетенции для всех выбранных HD; несовместимый транспорт; нераспознанный адрес; нет допустимого места в смене/окне; недоступный путь; неполные входные данные; не удалось включить в найденное решение. Последний случай не равен доказанной невыполнимости.

LLM и длинный текст не нужны. Библиотека может возвращать структурированные коды и факты, а приложение — строить короткий текст. Нельзя выдумывать причинность из одного сравнения «было/стало»: если выбранная библиотека не раскрывает шаги, объяснение должно ограничиваться проверенными фактами события и валидатора.

### 9.3. Ручное назначение и конфликты

Ручное назначение уже есть в приложении. В описании требуется «Назначена вручную», включая первое назначение. При пересечении с другой задачей того же исполнителя отметка и сообщение о конфликте должны отображаться **красным шрифтом** с номером заявки и временем пересечения.

Пересечение работ проверяется по плановым интервалам обслуживания, а не клиентским окнам. Для `[start, finish)` соприкосновение границ не является пересечением; однако между разными адресами может не хватать дороги — это отдельная ошибка. Отметка ручного назначения сама по себе не означает, что назначение навсегда закреплено.

Если ручной план уже содержит конфликт, валидатор должен обнаружить его. Автоматический решатель не может объявить такой план допустимым. Наличие красного предупреждения не определяет новое правило запрета ручного сохранения: существующий пользовательский процесс и исправление конфликта оцениваются отдельно.

### 9.4. Дополнительные отчёты и события приложения

- По D-031 назначения связывают оборудование заявок с исполнителями для кнопки «Требуемое оборудование». При переносе оборудования в сводке не должно быть двойного учёта старого и нового маршрутов. Для расходуемых устройств и многоразовых инструментов правило агрегации задаётся отдельно.
- По D-032 сохранённая смена статуса или проблема создаёт событие для журнала и 10-секундного всплывающего сообщения диспетчерам, отображающим нужное подразделение. Колокольчик слева от профиля открывает журнал, клик по сообщению — заявку. Регион показа — подразделение, не просто GMT-смещение.
- Эти функции реализует приложение. Решатель должен возвращать стабильные ID и понятные изменения; не требовать от библиотеки встроенной отрисовки, брокера сообщений или мобильных push.

## 10. Что искать в open-source решении

По терминологии задача близка к маршрутизации и расписанию выездных специалистов с окнами, навыками, разными режимами перемещения, открытыми маршрутами и динамическими срочными заявками. Для поиска пригодны термины:

```text
Technician Routing and Scheduling Problem (TRSP)
Vehicle Routing Problem with Time Windows (VRPTW)
Open VRP with heterogeneous fleet and skills
Fleet size minimization / lexicographic objectives
Dynamic VRP / urgent request insertion / response time minimization
Optional visits / unassigned jobs / fixed activities / warm start
```

Название класса не доказывает поддержку нашей комбинации правил. Исследовать варианты маршрутизации, constraint programming/CP-SAT, смешанного целочисленного программирования и эвристики вставки/локального поиска; у каждого проверить фактическую выразимость ограничений и поведение на сценариях ниже. Это направления исследования, не заранее выбранные библиотеки.

### Критерии отбора

| Возможность | Что подтвердить при исследовании |
|---|---|
| Начало внутри окна | Можно закончить после конца клиентского окна, соблюдая смену |
| Отказ от части заявок | Невместившиеся возвращаются явно, целевая функция максимизирует покрытие |
| Минимум исполнителей | Есть модель активации исполнителя, последовательные цели или обоснованное эквивалентное решение |
| Неоднородные исполнители | Все требуемые HD-компетенции, смены в разных поясах, стартовые точки, транспорт и внешние матрицы не сводятся к одному профилю |
| Открытые маршруты | Возврат на базу можно исключить из стоимости и времени |
| Приоритет аварии | Есть способ влиять на время начала/завершения, не только на штраф неназначения |
| Изменение готового плана | Можно сохранить фиксированную часть и перерасчитать остаток, использовать старое решение как старт |
| Ограничение времени поиска | Возвращается лучший найденный допустимый вариант и понятный статус завершения |
| Диагностика | Достаточно выходных данных для валидатора, причин неназначения и достоверного описания изменений |
| Интеграция | Подходит запуск через библиотеку, CLI или отдельный сервис с нормализованным JSON; оценивается стоимость адаптера |
| Open-source | Доступны код, лицензия и воспроизводимый запуск; ограничения лицензии и зависимости проверены по первоисточникам |
| Сопровождение | Указаны проверенная версия/commit, дата проверки, тесты и актуальность проекта |

Для каждой возможности отмечать: «поддерживается напрямую», «нужен адаптер/доработка», «не поддерживается», «не проверено». Наличие облачного бесплатного тарифа само по себе не означает доступность open-source решателя.

Недостаточно решения, которое только переставляет точки одного заданного маршрута, требует назначить все заявки любой ценой, считает только расстояние, не учитывает активацию исполнителей или не умеет защитить уже начатую часть дня.

Картографический сервис может быть внешним и коммерческим: это отдельный компонент. Исследуемый решатель должен по возможности принимать наши дорожные данные без обязательной зависимости от конкретного поставщика карт.

## 11. Проверочные сценарии для сравнения кандидатов

Все сценарии выполняются на заранее зафиксированных данных, с одинаковыми окнами, длительностями, матрицами, ограничениями и бюджетом поиска. Проверки ниже задают требуемое поведение, а не новый базовый алгоритм.

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| T01 | Приезд 09:40, окно с 10:00, обслуживание 40 минут | Ожидание 20 минут, работа 10:00–10:40 |
| T02 | Окно до 12:00, начало 11:50, работа 40 минут, смена до 18:00 | Назначение допустимо, окончание 12:30 |
| T03 | То же, но начало 12:01 либо смена заканчивается 12:20 | Автоматическое назначение недопустимо |

### Полный набор и масштабирование

1. Проверить малые управляемые примеры, где результат можно независимо проверить вручную.
2. Выполнить расчёты Востока, Юго-востока и Югоцентра, затем общий запуск на 203 новых заявках и исходных 35 карточках исполнителей.
3. Добавить события аварии, отмены и недоступности на сохранённый план в заданное время дня.
4. При необходимости создать явно синтетические увеличенные наборы, например 500 и 1000 заявок, сохраняя различие с исходными файлами Билайна.
5. Для стохастических методов провести несколько повторов с записанными seed; сравнить разброс результатов. Разделять время получения матриц, время решателя и время проверки/публикации.

Лимит времени первичного расчёта и перепланирования пока не установлен владельцем. Исследовать качество при нескольких измеренных бюджетах поиска; не назначать произвольное значение обязательным SLA.

## 12. Метрики и формат исследовательского вывода

Для каждого кандидата и сценария сохранить:

- входное число заявок, ошибки данных, запланированные и неназначенные с причинами;
- число нарушений каждого жёсткого ограничения;
- уникальных задействованных исполнителей и новых привлечённых при событии;
- километры каждого маршрута и всего плана; время в пути, ожидания и обслуживания отдельно;
- число назначенных/неназначенных аварий; время реакции и завершения каждой, максимум и распределение задержек;
- число переносов между исполнителями, изменений порядка и сроков, максимальный сдвиг времени;
- время получения матриц, решения и валидации, память, статус поиска, воспроизводимость;
- использованные версии, параметры, политика целей, допущения и необходимые доработки адаптера.

Не сводить весь отчёт к единственному «баллу качества». Допустимость, покрытие, ресурс и реакция на аварии должны оставаться видимыми. Более короткий маршрут с меньшим покрытием не объявлять улучшением без пояснения.

**Ожидаемый итог исследования:** короткий список кандидатов с проверенными первичными источниками; таблица соответствия требованиям; воспроизводимые результаты сценариев; рекомендуемый вариант и причины выбора; объём интеграции/доработок; ограничения и решения по открытым компромиссам. Если готовая библиотека не покрывает комбинацию правил, описать составное решение: библиотека + предметная нормализация + вставка аварий/проверка/диагностика.

## 13. Вопросы, которые нельзя скрыть настройками библиотеки

1. **Нормативы Q-044:** состав дорожных 20 минут и точное сопоставление четырёх категорий с BK/HD. Для экспериментов использовать явно указанную рабочую модель раздела 4.
2. **Срочность против ресурса/покрытия:** порядок и допустимая цена ускорения аварии; несколько одновременных аварий. Сравнить политики раздела 6 и показать последствия, не подменяя решение случайными штрафами.
3. **Параметры синтетического штата:** компетенции ВК/HD, смены, часовые пояса, транспорт и дополнительные допуски отсутствуют в исходных CSV; фиксировать их в версии тестового набора.
4. **Дорожная модель и скорость:** статическая/зависимая от времени матрица, точность общественного транспорта, бюджеты вычислений. Эти допущения нужны для честного сравнения, но не блокируют подготовку экспериментального стенда.

5. **Комбинации HD и оборудование:** правила общего времени, количеств и общих операций при нескольких работах не выводятся из первоначальных четырёх нормативов. Указать рабочее правило эксперимента и способ его замены.
