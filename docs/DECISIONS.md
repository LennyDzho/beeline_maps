## D-001. Изменение подтверждённого клиенту визита

- Статус: принято.
- Решение: подтверждённый клиенту визит считается защищённым от автоматического изменения.
- Оптимизатор может предложить изменение такого визита, но не может применить его самостоятельно.
- Для применения изменения диспетчер должен явно подтвердить, что сообщил клиенту.
- Система сохраняет автора подтверждения, время, старое и новое расписание и причину изменения.
- Пока подтверждения нет, действующим остаётся старый план.

## D-002. Картографический сервис для MVP

- Статус: предварительно принято; пересмотреть после получения полного задания хакатона.
- Решение: использовать API-платформу 2ГИС как основной российский геосервис для MVP.
- Планируемые компоненты: MapGL JS API, Geocoder API, Distance Matrix API и Routing API.
- TSP API 2ГИС использовать как быстрый эталонный или резервный планировщик, но не связывать с ним доменную модель приложения.
- Доступ к геосервису реализовать через собственные интерфейсы-адаптеры, чтобы можно было заменить 2ГИС без изменения бизнес-логики.
- Бесплатный демо-ключ не создавать заранее: он выдаётся один раз и действует один месяц.

## D-003. Разделение планирования и картографии

- Статус: принято.
- Решение: карта не является источником бизнес-правил.
- Картографический слой отвечает за геокодирование, дорожное время, расстояния и геометрию маршрута.
- Планировщик отвечает за квалификации, оборудование, транспорт, SLA, статусы визитов и разрешения диспетчера.

## D-004. Независимые контракты провайдеров

- Статус: принято.
- Решение: контракты реализуются отдельным TypeScript-пакетом `@mmi/provider-contracts` без зависимости от веб-фреймворка или SDK карт.
- Внутренний формат координат — объект `{ lat, lon }`; массивы координат поставщика допускаются только внутри адаптеров.
- API-ключи, HTTP-ответы и SDK-типы поставщика не входят в публичные контракты.
- Каждый адаптер публикует профиль возможностей, включая неподдерживаемые ограничения.

## D-005. Граница использования TSP API 2ГИС

- Статус: принято.
- Решение: навыки, смены, окна и закреплённые за инженером ресурсы могут отображаться на возможности TSP API.
- Общий пул оборудования и транспорта, блокировка подтверждённых визитов, аудит согласований и итоговое объяснение решения остаются в приложении.
- Начальный маршрут внешнего API не считается гарантией неизменности подтверждённого визита.

## D-006. Модель доступа

- Статус: предварительно принято для MVP.
- Решение: использовать роли `platform_admin`, `org_admin`, `dispatcher` и `performer`.
- RBAC дополняется серверными ограничениями по организации, назначенному исполнителю, состоянию объекта и бизнес-подтверждениям.
- Роль и идентификаторы области доступа из клиентского запроса не считаются доверенными.
- Учётная запись `User`, сотрудник планирования `Worker` и доступ к организации `Membership` являются разными сущностями.

## D-007. Регистрация только по приглашению

- Статус: предварительно принято для MVP.
- Решение: открытой регистрации нет; исполнитель активирует доступ по одноразовому приглашению, привязанному к заранее созданному `Worker`, организации, роли и телефону.
- Телефон подтверждается OTP. При отсутствии приглашения учётная запись исполнителя не активируется.
- Роль и квалификации назначает организация, пользователь не выбирает их при регистрации.

## D-008. Раздельные уровни подтверждения данных

- Статус: предварительно принято для MVP.
- Решение: отдельно хранить подтверждение контакта, принадлежности к карточке сотрудника, версии анкеты и квалификаций.
- OTP подтверждает только владение контактом, но не личность, трудовые отношения или навыки.
- Расхождение в анкете создаёт запрос на исправление и не меняет эталонные данные автоматически.

## D-009. Android-приложение исполнителя

- Статус: предварительно принято для MVP.
- Решение: сделать нативное приложение на Kotlin и Jetpack Compose с UDF, ViewModel, Room и WorkManager.
- Рабочие экраны читают данные из Room; сервер остаётся источником истины, а изменения offline отправляются идемпотентной очередью после восстановления сети.
- Версия для iOS и непрерывная фоновая геопозиция не входят в MVP.

## D-010. Push-уведомления Android

- Статус: предварительно принято для MVP.
- Решение: использовать Firebase Cloud Messaging через серверный HTTP v1 API и собственный интерфейс `PushProvider`.
- Для MVP официально поддерживаются устройства с совместимыми Google Play services; без них приложение сохраняет ручную синхронизацию, но не обещает push.
- Android 13+ запрашивает `POST_NOTIFICATIONS` после объяснения пользы; отказ не блокирует приложение.

## D-011. Push не является источником бизнес-состояния

- Статус: принято.
- Решение: доменное изменение и запись события уведомления фиксируются в одной транзакции через transactional outbox.
- Push содержит только идентификаторы события и сущности, версию и sync hint, без клиентских персональных данных.
- Клиент дедуплицирует события и получает актуальное состояние из API, поскольку push может потеряться, повториться или прийти не по порядку.
- Принятие сообщения push-провайдером не считается подтверждением пользователя; для этого требуется явный `ack` или бизнес-переход.

## D-012. Проверяющий отчёта задаётся видом работ

- Статус: спроектировано как дополнительная функция; не входит в базовый MVP.
- Решение: физическое завершение работ и учётное закрытие визита являются разными состояниями.
- Администратор в каждой версии вида работ выбирает ровно один способ проверки: диспетчер либо конкретная ИИ-модель из разрешённого списка.
- В ручном режиме диспетчер принимает отчёт или возвращает его на доработку. В AI-режиме ответ `accepted` автоматически закрывает задачу, а `not_accepted` или техническая ошибка направляет отчёт диспетчеру.
- Отправленная и принятая ревизия неизменяема; исправление создаёт следующую ревизию с полной историей.
- Только принятое выбранным проверяющим состояние закрывает визит в учётном смысле; ожидание проверки не блокирует исполнителя для последующего маршрута.

## D-013. Гео-, фото- и видеофиксация FSM

- Статус: спроектировано как дополнительная функция; не входит в базовый MVP.
- Решение: вид работ определяет обязательные точки разовой геофиксации, категории и количество фото/видео, способ захвата и технические ограничения.
- Эталонная координата объекта и фактическая координата устройства хранятся раздельно; расстояние и аномалии рассчитывает сервер.
- При реализации дополнительного модуля используется foreground location в момент действия, без непрерывного фонового трекинга.
- Бинарные материалы хранятся в закрытом object storage; отправить отчёт можно только после серверного подтверждения всех обязательных материалов.

## D-014. Внешняя ИИ-проверка через API

- Статус: спроектировано как дополнительная функция; не входит в базовый MVP.
- Решение: система не разрабатывает и не обучает модели; заказчик добавляет собственные API-подключения в каталог организации.
- Серверный `ReportVerificationProvider` передаёт поля отчёта, гео-метаданные и фотографии и принимает бинарный ответ `accepted | not_accepted`.
- `accepted` атомарно принимает отчёт и закрывает задачу. `not_accepted`, timeout, невалидный ответ или ошибка направляют отчёт диспетчеру на ручную проверку.
- Видео сохраняется как доказательство, но в первом прототипе модуля не передаётся модели.
- Для демонстрации дополнительного модуля предусмотрена заглушка `always_not_accepted`, которая всегда возвращает `not_accepted` и показывает полный маршрут через диспетчера без настоящей ИИ-модели.

## D-015. Версионирование настроек вида работ

- Статус: спроектировано как дополнительная функция; не входит в базовый MVP.
- Решение: шаблон отчёта, гео-/медиаполитика и `reviewerType=dispatcher|ai_model` публикуются как неизменяемая `WorkTypeVersion`.
- Визит сохраняет ссылку на конкретную версию; изменение настроек действует только для новых назначений и не переписывает исторические требования.
- `org_admin` управляет API-подключениями моделей своей организации и выбирает проверяющего в виде работ; секреты хранятся server-side, диспетчер не меняет эти настройки.

## D-022. Перепланирование только не начатой части работ

- Статус: принято. Источник: ответ владельца на Q-042, 15.09.2026.
- После первоначальной загрузки источником оперативного состояния служат статусы нашего приложения.

## D-026. Совместная работа диспетчеров и атомарная публикация плана

- Статус: принято как требование к реализации. Источник: явное согласование владельца проекта, 15.09.2026. ТЗ не задаёт количество диспетчеров и правила одновременного редактирования; это решение для нашего приложения.
- Область совместной работы — общий план по всем доступным подразделениям на выбранную дату. Уточнение владельца от 15.09.2026 заменяет прежнюю проверку только внутри одного подразделения. Разделение пулов исполнителей по подразделениям не ограничивает область проверки конфликтов общего плана.
- Оптимизация создаёт общий черновик на основе согласованного снимка текущего состояния всех участвующих подразделений. С черновиком сохраняются их идентификаторы, исходные версии и состав данных, использованных при расчёте. Сам расчёт не меняет действующие назначения.
- Если другой диспетчер изменил заявки или назначения в любом из участвующих подразделений после получения снимка, в том числе во время расчёта либо между расчётом и публикацией, публикацию общего плана отклонять с сообщением: «План изменён другим пользователем. Обновите данные и повторите расчёт».
- Проверка актуальности всех участвующих подразделений и применение всего общего плана выполняются атомарно. При конфликте не менять ни действующие назначения, ни статус плана; исключить частичную публикацию, в том числе только по части подразделений. Раздельная проверка перед несколькими независимыми пакетами записи не обеспечивает это правило.
- Защита должна учитывать изменение состава заявок, исходных требований и доступности исполнителей, влияющих на расчёт, а также публикацию другого плана той же области. Ручное редактирование и публикация используют согласованный механизм версий, чтобы ни один из путей записи не затирал более свежие изменения.
- Проверки реализации: общий расчёт включает все доступные подразделения без назначений между ними; правка в любом участвующем подразделении во время расчёта или после его завершения сохраняется и вызывает конфликт общего плана; из двух конкурирующих публикаций на основе одного снимка применяется только одна; ошибка применения не оставляет частично опубликованный план. Проверить пункт «Все подразделения» у диспетчера и администратора и переключение между общим и отдельным срезом без изменения области общего запуска.
- Существующие правила D-001 о подтверждённых визитах и D-022 о начатой части дня сохраняются. Фиксация решения в документах не означает, что защита уже реализована в коде.

## D-027. Формат результата и отображение снятых назначений

- Статус: принято как требование к доработке. Источник: уточнение владельца проекта от 15.09.2026. В этом запросе требуется только фиксация требований.
- По оценке владельца уже есть: упорядоченные заявки исполнителя с плановым прибытием/началом и пробегом; назначенный исполнитель либо «не назначена» у заявки; количество задействованных исполнителей и километраж по исполнителям/всему плану в диспетчерской. Сохранить эти возможности; не считать их отсутствующими.
- Доделать явную понятную причину для каждой неназначенной заявки. Причина отражает данные и результат расчёта, а не только технический код ошибки.
- Доделать наглядное сравнение после перепланирования: изменение назначения, порядка заявок и маршрута. Одной отметки о новом исполнителе недостаточно.
- При переносе из исполнителя А к исполнителю Б убрать заявку из активного списка рассчитанного маршрута А, но показать у А отметку «Заявка снята» с номером заявки, причиной и новым исполнителем. У Б показать заявку в новом месте маршрута с отметкой «Перенесена с исполнителя А» и связанной причиной переноса.
- Отметка снятия должна быть видна и у исполнителя, у которого после пересчёта не осталось активных заявок. Она относится к сравнению, не считается активной остановкой и не увеличивает число заявок, нагрузку или километраж нового маршрута.
- Если заявка снята без нового назначения, у прежнего исполнителя показать «Снята, не назначена» с причиной; в общем списке неназначенных показать ту же заявку и объяснение. Снятие назначения не равно отмене самой заявки.
- Изменение только порядка или маршрута также отражать явно. Существующую отметку о переносе у нового исполнителя сохранить; дополнить её отображением снятия у прежнего. Краткую причину требовать для переноса/перераспределения и изменения сроков по D-028; описание выбора при первом назначении не требуется.
- В черновике формулировать изменения как предлагаемые: «Будет снята / будет перенесена». Действующие назначения меняются при публикации по D-026. После публикации результат изменения остаётся доступен в сравнении с предыдущим планом.

## D-028. Расчёт с минимальным ресурсом, срочные аварии и причины изменений

- Статус: принято. Источник: явные ответы владельца на Q-041, 17.09.2026. Q-041 закрыт; повторно подтверждать у кейсодателя эти пункты не требуется. Это требования к будущей реализации, не отчёт о внесённых изменениях кода.

### Распределение и сравнение

- Отдельный последовательный базовый алгоритм из §2.3 ТЗ и сравнение с ним не ожидаются. Снять WEB-06 из обязательного плана; не создавать `SequentialBaselineEngine` ради демонстрационного сравнения.
- Цель — распределить заявки с минимальным необходимым ресурсом при соблюдении временных окон, навыков, транспорта, смен и остальных ограничений. Минимальный ресурс для текущей модели — число уникальных задействованных исполнителей. Не снижать число назначений только ради уменьшения этого показателя; при невозможности распределить все сохранить явные причины неназначения. Километраж каждого исполнителя и общий показывать по прежним требованиям.
- Сохранить расчёт собственных вариантов, проверку ограничений, метрики и сравнение предыдущего плана с новым после перепланирования. Предыдущий опубликованный план и история назначения не являются отменённым базовым алгоритмом.

### Аварии и перепланирование

- Возможность перепланирования сохраняется. Аварийная заявка срочная, её временное окно — сутки на дату планирования в Europe/Moscow; выполнить как можно быстрее. Суточное окно не означает суточную длительность работы и не оправдывает откладывание до конца дня. Исходное окно из CSV сохранять для происхождения; в расчёте аварии применять согласованное суточное окно, включая случаи более узкого исходного интервала.
- Предложенный владельцем способ — фильтр способных выполнить аварию исполнителей и поиск допустимых вставок в их маршруты. Это основа эвристики, не требование использовать конкретную библиотеку.
- Фильтр учитывает подразделение, навыки, обязательный транспорт и доступность. Для каждого подходящего исполнителя проверить позиции между запланированными работами с дорогой, ожиданием, нормативом и документами; допустимую возможность до первого/после последнего визита также учитывать. Ищем самое раннее допустимое выполнение, не только свободное место в конце дня.
- При событии использовать фактическое время события и состояние исполнителя; не назначать в прошедшее время. Проверять также окна и смены всех затронутых заявок. При необходимости переставлять ещё не начатые работы с короткими причинами; защиты начатых поездок/работ и подтверждённых визитов D-001/D-022 сохраняются.
- Если допустимая вставка не найдена, показать понятную причину; не нарушать ограничения молча. Не объявлять математическую невозможность только по неудаче эвристики.

### Когда нужна причина

- Первое назначение — заявка впервые за всю свою историю получает исполнителя. Для него не нужны описание выбора, длинное рассуждение или текст в стиле LLM. Карточка сохраняет обычные данные: исполнитель, маршрут, плановое время, окно и статус.
- После снятия и повторного назначения заявка не становится «первоначальной» снова. Признак прежнего назначения определять по сохраняемой истории; просмотр или пересчёт неопубликованного черновика не делает первое назначение свершившимся.
- Для переноса/перераспределения, снятия исполнителя и любого последующего изменения сроков нужна краткая причина. В том числе при прежнем исполнителе: изменились плановое прибытие/начало/окончание, дата либо уже сохранённое клиентское окно; причина нужна и для ручной правки, и для пересчёта. Первичное заполнение полей при создании заявки не является правкой ранее заданных сроков.
- Изменение времени из-за сдвига предыдущего визита требует причины у каждой затронутой заявки, а не только у аварийной. Показывать изменённые значения «было → стало» и короткую причину, например «Начало 14:00 → 14:30: у исполнителя появилась срочная авария». Текст и значения должны соответствовать реальному расчёту.
- При ручной правке указывать краткую причину изменения; при автоматической брать её из события и диагностики. Причины хранить с изменением, воспроизводить после открытия плана, сохранять при публикации. Сам текст не требует LLM.
- У прежнего исполнителя показывать снятие с причиной, у нового — перенос с указанием прежнего исполнителя и той же связанной причиной (D-027). В черновике изменения предложенные; действующие назначения меняются при атомарной публикации D-026.
- Для каждой неназначенной заявки понятная причина по D-027 сохраняется, в том числе до первого назначения: исключение относится к объяснению первого успешного выбора исполнителя.

### Проверка реализации

- Первое успешное назначение — без объяснения выбора; неназначенная заявка — с причиной.
- Перенос A → Б — краткая причина и отображение у обоих; повторное назначение после снятия не считается первым.
- Исполнитель не меняется, время сдвинуто — «было → стало» и причина; проверить ручную правку и цепочку сдвигов от срочной аварии.
- Авария с суточным окном вставляется в раннюю допустимую позицию среди способных исполнителей; начатые/защищённые работы, чужие окна и смены не нарушены.
- Пересчёт черновика до первой публикации не создаёт ложной истории исполнений или искусственных «повторных» назначений.

## D-029. Ручное назначение и красное предупреждение о пересечении

- Статус: принято как уточнение требований, 17.09.2026. Источник: владелец проекта. Ручное назначение уже работает: диспетчер открывает заявку и выбирает исполнителя. Это состояние зафиксировано со слов владельца, без новой проверки кода; отдельную функцию назначения заново разрабатывать не требуется.
- В описании заявки явно показывать «Назначена вручную». Отметка нужна и при первом назначении: это указание способа назначения, а не объяснение выбора исполнителя. Поэтому она совместима с исключением для первого назначения в D-028.
- Если вручную назначенная заявка пересекается по плановому времени с другими задачами того же исполнителя, отметку назначения и сообщение о конфликте обязательно показывать **красным шрифтом**. Одной красной рамки, заливки или иконки недостаточно.
- Сообщение должно указывать, с какой заявкой возник конфликт и какие времена пересекаются. Пример: «Назначена вручную. Пересечение с заявкой №123: 14:30–15:00». Номер и время брать из фактического расписания.
- Пересечение проверять по плановым интервалам работ, включая документы, а не только по совпадению клиентских окон. Проверять другие задачи выбранного исполнителя; саму заявку не сравнивать с собой. Для интервалов [начало, конец) пересечение есть, если начало A < конец B и начало B < конец A. Соприкосновение концов не является пересечением работ; нехватка времени дороги — отдельный конфликт маршрута.
- Проверку обновлять при ручном назначении, смене исполнителя и изменении сроков затронутых задач. Существующий конфликт должен оставаться виден после сохранения и повторного открытия. После устранения конфликта красное предупреждение снимается, отметка «Назначена вручную» сохраняется у ручного назначения.
- При последующем переносе или изменении сроков сохраняется требование краткой причины D-028: отметка ручного назначения указывает способ действия, но не отменяет причину изменения.
- Проверка реализации: первое ручное назначение без пересечения — обычная отметка; с пересечением — красный текст с номером конфликтующей заявки; сдвиг времени создаёт/устраняет предупреждение; после открытия состояние воспроизводится. Уточнение касается отображения; новых правил запрета сохранения здесь не вводится.

## D-030. Часовой пояс каждого исполнителя

- Статус: принято, дополнительное требование владельца вне ТЗ, 17.09.2026.
- В карточке исполнителя указать временной регион GMT±. Относящееся к региону время вводится и отображается в его локальном времени; часовой пояс влияет на расчёт, а не служит декоративной подписью.
- Для расчётов приводить моменты к единой шкале, сохраняя локальный часовой контекст. Часовой пояс браузера/сервера не меняет смысл ввода. В сводке разных регионов явно показывать пояс.
- Смена исполнителя/пояса не меняет молча абсолютное время обещанного визита. Суточное окно аварии относится к локальным суткам заявки/плана; для имеющегося набора это GMT+03:00, но общий продукт не ограничен Москвой.
- Часовой контекст неназначенной заявки и способ хранения зоны определяются в реализации с сохранением однозначного времени. [Правила и приёмка](ADDITIONAL_PRODUCT_REQUIREMENTS.md#1-часовой-пояс-каждого-исполнителя--d-030--web-14).

## D-031. Оборудование вида работ и сводка по исполнителям

- Статус: принято, дополнительное требование владельца вне ТЗ, 17.09.2026.
- Для каждого вида работ задавать требуемое оборудование; тот же перечень указывать в заявке. При нескольких HD учитывать все выбранные работы и версию применённых требований.
- В диспетчеризации добавить кнопку «Требуемое оборудование» со сводным отчётом по оборудованию, сгруппированным по исполнителям.
- Предлагаемый охват отчёта — выбранная дата/план и срез подразделений, явно подписанные. Неназначенные потребности показывать отдельно. Переназначение переносит потребность между группами без двойного учёта.
- Количества, расходуемость/повторное использование и складские остатки сообщением 17 сентября не заданы. Уточнение 19 сентября **D-034** вводит обязательную проверку полученного оборудования после выезда. ## D-032. Всплывающие сообщения и журнал диспетчера

- Статус: принято, дополнительное требование владельца вне ТЗ, 17.09.2026.
- При смене статуса заявки или появлении проблемы показывать диспетчерам, отображающим её регион, всплывающее сообщение на 10 секунд. Клик открывает соответствующую заявку для просмотра/редактирования по правам.
- Слева от кнопки профиля добавить колокольчик, открывающий журнал этих сообщений. Исчезновение всплывающего окна не удаляет запись журнала.
- Рабочее толкование региона — подразделение в фильтре диспетчеризации D-025. В «Все подразделения» показывать события всех доступных отображаемых подразделений; не маршрутизировать сообщения только по совпадению GMT-смещения.
- Изменение статуса и отдельная проблема являются событиями; повторная доставка одного ID не создаёт дублей. Использовать принцип надёжной записи события D-011. Таймер каждого сообщения отсчитывается от его показа.
- Журнал доступен после повторного открытия и отражает события, даже если всплывающее сообщение было пропущено. [Состав, область показа и приёмка](ADDITIONAL_PRODUCT_REQUIREMENTS.md#3-сообщения-диспетчеру-и-журнал--d-032--web-16).

## D-033. Иерархия ВК и набор HD у заявки и исполнителя

- Статус: принято, дополнительное требование владельца вне ТЗ, 17.09.2026.
- ВК (BK в CSV) — первый фильтр/ниспадающий список; HD — второй уровень с выбором галочками. У заявки одна ВК-категория и несколько требуемых HD-работ.
- У исполнителя выбирать ВК и галочками отмечать доступные ему HD. Переключение ВК открывает другую группу, не стирая уже заданные компетенции.
- «Заказ подключения/Дозаказ оборудования» — две HD-работы в одной заявке. «Заказ подключения» и «Заявка на подключение» — один канонический тип с алиасами. Две работы не создают две заявки/два выезда автоматически.
- Для автоматического назначения нужны все HD выбранной заявки в её ВК, а не только совпадение категории или одного типа. Крупные навыки исходного ТЗ могут остаться совместимой группировкой; не подменять ими подробную проверку.
- Длительность сочетания HD и правила агрегации оборудования определить явно; сумма четырёх исходных BK-нормативов не принимается автоматически. Это уточняет прежнюю целевую модель одного HD/навыка у заявки.
- [Каталог, импорт и приёмка](ADDITIONAL_PRODUCT_REQUIREMENTS.md#4-категория-вк-и-несколько-типов-hd--d-033--web-17).

## D-034. Оборудование бригады после выезда

- Статус: принято, явное уточнение владельца 19.09.2026.
- Бригада получает оборудование в офисе сразу на весь рабочий день после планирования, до начала работ.
- При перепланировании после выезда автоматически назначать только заявки, для которых у бригады есть необходимое оборудование. Требования всех HD обязательны.
- Новое назначение не пополняет уже полученный комплект. Потребность плана и оборудование у бригады — разные данные.
- Ручное назначение при нехватке разрешено; в плане красным шрифтом указать, какого оборудования у бригады нет. Дополнительно показать предупреждение в карточке и сводке.
- Количественное списание расходуемых материалов отдельно не задано. Запрошено уточнение; текущая реализация проверяет наличие видов оборудования, не выдумывает количества и складские остатки.
