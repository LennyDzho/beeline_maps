# Автотесты «Марш!»

Основной запуск из корня проекта:

```powershell
pnpm qa
```

Он проверяет TypeScript, ESLint, сборку, маршрутизацию, серверные API, вход, отчёты, справочники, мобильные команды, валидацию медиа и стартовую инициализацию. Выполняется настоящий собранный Worker с SQLite в памяти, а не запросы к рабочему `localhost:3000`.

Не останавливается на первом дефекте: остальные независимые проверки выполняются, после чего возвращается ненулевой код. Если сборка не прошла, зависимые проверки помечаются `blocked`, а не запускаются на устаревшем артефакте.

## Расширенный запуск

```powershell
pnpm qa --browser --android
```

- `--browser`: сценарии UI-01–UI-26 в headless Chromium/Edge, включая доступность исполнителя, четыре транспорта, согласование клиентских переносов и комплект оборудования после выезда. Сервер тестов получает случайный порт на `127.0.0.1` и отдельную базу в памяти. Используется новый браузерный профиль, не профиль пользователя.
- `--android`: сборка debug APK, JVM unit-тесты, Android Lint и **компиляция** instrumentation-тестов. APK не устанавливается, эмулятор не очищается, device-тесты не запускаются.

Для браузерных тестов нужен установленный пакет `playwright` и Chromium либо системный Edge/Chrome. Можно использовать заранее установленный модуль без изменения зависимостей проекта:

```powershell
# Проверенное окружение этого компьютера; на другой машине укажите её путь.
$env:PLAYWRIGHT_MODULE_PATH = 'C:/Users/vadim/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/node_modules/playwright'
$env:BROWSER_CHANNEL = 'msedge'
pnpm qa --browser --android
```

Если `PLAYWRIGHT_MODULE_PATH` отсутствует, тесты разрешают обычный установленный модуль `playwright`. Если `BROWSER_CHANNEL` отсутствует, используется Chromium из установки Playwright. Недоступность браузера считается ошибкой запуска, а не успешной проверкой.

Android использует существующий `apps/android/build.ps1`: JDK из `JAVA_HOME` или Android Studio, SDK из `ANDROID_HOME` или стандартной установки. Для не-ASCII пути создаётся временный снимок исходников. На Linux/macOS Android-этап общего запуска помечается `blocked`; соответствующие Gradle-задачи следует запускать нативно. Недостающие зависимости Gradle могут требовать сетевого доступа.

## Результаты

Каждый запуск создаёт отдельный каталог `.tmp/qa/<UTC-дата-время>-<PID>/`:

- `summary.json`: общий результат, результат каждого этапа, код выхода, длительность, путь к журналу;
- `*.log`: полный вывод проверок, включая TAP с именами и количеством тестов;
- снимки браузерных сценариев: `apps/web/.tmp/qa-browser/UI-01.png` … `UI-29.png` (последний запуск);
- Android: `apps/android/app/build/test-results/testDebugUnitTest/`, `app/build/reports/lint-results-debug.html`.

Временные результаты исключены из Git. Постоянные документы: [сценарии](TEST_SCENARIOS.md) и [результат проверки 11.09.2026](TEST_REPORT_2026-09-11.md).

## Отдельные проверки

Составные отчёты: `composite-report.test.mjs` проверяет версии шаблонов, все HD-поля, материалы, отправку и приёмку; UI-27/28 — редактор требований и просмотр отчёта. `dataset-transition.test.mjs` проверяет откат поздней ошибки при замене набора, сохранение доступа, запрет неизвестных таблиц/неперенесённых интеграций и безвредный повтор импорта. Эти сценарии входят в общий QA.

`MobileDetailsTest` (3 сценария) и `CompositeConnectedTest` прошли 21 сентября на отдельном временном Android-эмуляторе. Последний тест запускается только с `isolatedHost=true`, сервером `http://10.0.2.2:<временный порт>` и параметрами одноразовой учётной записи из `tests/helpers/composite-device-server.mjs`. Сервер использует БД в памяти, проверяет контрольные суммы загруженных фото/видео и принимает отчёт через API диспетчера. Этот тест очищает настройки Android-приложения, поэтому его запускают **только на отдельном временном эмуляторе**, не в пользовательской сессии. Полный `-DeviceTests` не требуется.

```powershell
pnpm test                           # алгоритмы/провайдеры, включая реальный OR-Tools
pnpm --dir apps/web test             # существующий базовый web-набор со сборкой
pnpm --dir apps/web test:api          # новый интеграционный набор со сборкой
pnpm --dir apps/web test:browser      # браузерные сценарии со сборкой
pnpm --dir apps/web test:workflow     # мобильные команды и безопасный seed
pnpm --dir apps/web test:reports
pnpm --dir apps/web test:qualifications
pnpm --dir apps/web test:media
./apps/android/build.ps1 -CompileDeviceTests
```

Быстрый повтор одного сценария после успешной сборки:

```powershell
cd apps/web
node --test --test-name-pattern='PLAN-04' tests/application-api.test.mjs
node --test --test-name-pattern='ADM-02' tests/application-api.test.mjs
```

Исторические дефекты `PLAN-04`, `ADM-02` и ESLint из отчёта 11.09.2026 исправлены; тесты сохранены и проходят. Актуальный результат каждого запуска проверяется в его `summary.json`, а не по историческому отчёту.

## OR-Tools и приёмка синтетики

Для общего QA нужен Python с зависимостями [сервиса решателя](../services/optimizer/README.md). `OPTIMIZER_TEST_PYTHON` задаёт полный путь к интерпретатору. По умолчанию используется уже установленный `algorithm-research/benchmark/.venv` (на Windows `Scripts/python.exe`, на Linux `bin/python`). Зависимости не устанавливаются незаметно: отсутствие среды считается ошибкой запуска.

Python-проверки включены в `pnpm qa`; они вызывают настоящую библиотеку и временный HTTP-сервер на loopback. Серверные сценарии `SOLVER-01–03` проверяют настройки, черновик и публикацию. `SOLVER-04` импортирует весь манифест в одноразовую базу и проверяет 203 планируемые заявки с сохранённой направленной дорожной матрицей. Это проверка приложения, не возобновление исследовательской серии. Она занимает примерно три бюджета поиска по 15 секунд; точное время зависит от компьютера. Сводка сохраняется в `apps/web/.tmp/beeline-planning-acceptance.json`. Внешние API, рабочая база и результаты исследования не меняются. Проверка не подтверждает оптимальность, геометрию или актуальность пробок.

## Границы и безопасность

Общий план проверяют `common-plan.test.mjs` (COMMON-01–12) и UI-22/23: независимые пулы, единая публикация, гонки данных/прав, откат второй половины записи, клиентские подтверждения, часовые пояса, фильтры, оборудование и уведомления. `SOLVER-04` публикует три подразделения одной операцией.

`cold-start.test.mjs` (COLD-01) запускает настоящий Worker с одной схемой авторизации, без предварительного применения предметных миграций. COLD-02/03 в `startup-seed.test.mjs` проверяют защиту существующих данных, гонку перед перестройкой, откат и повтор. Все базы одноразовые и находятся в памяти.

1. `isolated-worker.mjs` открывает только `new DatabaseSync(":memory:")`. Рабочие `.wrangler`, `.dev.vars`, SQLite-файлы, пароли и ключи не читаются.
2. Все миграции применяются к одноразовой базе. Затем штатная инициализация создаёт демоданные **только в ней**. Каждый сценарий откатывается через savepoint; D1 `batch` воспроизводится вложенным savepoint с откатом при ошибке.
3. HTTP-ответы геокодирования и OSRM фиксированы. Любой неожиданный внешний `fetch` отклоняется. Эти тесты проверяют обработку протокола, но не доступность подписки, правильность реальных улиц, пробки или точность ETA.
4. Браузер блокирует внешние запросы, включая MapGL, шрифты и тайлы. Проверяются интерфейс, резервное состояние карты и размеры контейнера; полноценная карта 2ГИС и внешний иконочный шрифт не входят в визуальную проверку.
5. `DemoFlowTest` и `ConnectedFlowTest` очищают настройки приложения; второй также отправляет данные на сервер. Они **не включены** в автоматический запуск на пользовательском эмуляторе. Нужны отдельный QA-эмулятор и независимый тестовый backend.
6. `verify-mobile-api.mjs`, `setup-mobile-demo.mjs`, `cleanup-mobile-qa.mjs` и миграционные скрипты существующего проекта не вызываются из QA: они могут менять рабочие данные.
7. Нет публикации сайта, установки APK, сброса базы, удаления пользовательских файлов или изменения бизнес-логики приложения.

Это функциональный регрессионный набор, не доказательство полного покрытия, нагрузочный тест или законченный аудит безопасности.

Сравнение геометрии: `route-geometry.test.mjs` (GEOMETRY-01–05), UI-25/26. Проверяются сохранённый исходный порядок, обе дорожные линии, публикация/перезагрузка, отсутствие ложной геометрии и красные конфликты по актуальным назначениям. MapGL и маршрутный сервис заменены изолированными ответами.
