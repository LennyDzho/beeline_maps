# Единый API оптимизации

Приложение вызывает `OptimizationEnginePort.optimize(problem, options)` из
`@mmi/provider-contracts`. В `apps/web/app/lib/server/planning/providers.ts`
выбирается один адаптер: OR-Tools, PyVRP или 2ГИС TSP.
Источник дорожных матриц и геометрии выбирается независимо: OSRM или 2ГИС.

Для OR-Tools и PyVRP общий код находится в `service-optimizer.ts`:
подготовка матриц, компетенций и оборудования, HTTP, тайм-ауты, восстановление
дорожных метрик, проверка расписания и согласований. Файлы `ortools-optimizer.ts`
и `pyvrp-optimizer.ts` задают конкретный метод. Python-сервис принимает тот же
`POST /v1/solve` с `engine: "ortools" | "pyvrp"`. Отсутствующий `engine` означает
OR-Tools для совместимости старых клиентов; неизвестное значение отклоняется.
Ответ содержит выбранный метод, версию библиотеки и политику. Подмена метода
в ответе отклоняется. При ошибке сохраняется предыдущий черновик.

## PyVRP: аварии и перепланирование

Установлена версия `pyvrp==0.14.0`. Нативный поиск строит назначения и порядок
по направленным матрицам каждого исполнителя, временным окнам, сменам,
пригодности, фиксированным работам и лимитам. Для поисковой модели объединяются
раздельные окна и временно опускаются перерывы. Затем адаптер восстанавливает
точное расписание и исправляет назначения вставками и переносами:

- Начало работы входит в одно из исходных окон и не предшествует `releaseAt`.
- Поездка и обслуживание не пересекают перерывы; ожидание может их пересекать.
- Фиксированные работы сохраняют исполнителя и время.
- Соблюдаются конец смены, возврат при заданной конечной точке, лимиты количества
  заявок, времени движения и расстояния, компетенции и полученное оборудование.
- Аварии сравниваются по той же иерархии, что в настройках: охват заявок,
  охват аварий, затем задержка аварий/дополнительные бригады в выбранном порядке,
  затем расстояние. Сравнение в адаптере выполняется кортежами без округления весов.

Это **PyVRP с прикладным улучшением аварийного расписания**, а не нативная функция
штрафа за задержку аварии внутри PyVRP. На нативный поиск отводится 65% оставшегося
бюджета после построения модели, остальное — проверке, вставкам и переносам.
Поиск эвристический: глобальная оптимальность и полное назначение при любом
бюджете не гарантируются. Финальный общий валидатор приложения независимо
проверяет ограничения перед сохранением. OR-Tools внутри PyVRP-адаптера не запускается.

Общий слой приложения сохраняет начатые, приостановленные и закрытые работы.
Оставшаяся очередь рассчитывается с выбранного момента и подтверждённой точки
освобождения занятой бригады. Без актуальной оценки освобождения занятая бригада
не участвует в новой очереди. Подтверждённый клиенту визит требует согласования
изменений перед публикацией. Создание аварии само по себе не публикует новый план.

## Настройка и запуск

Администрирование → Настройки → Настройки планирования → Алгоритм распределения
→ **PyVRP**. Выберите приоритет аварий и сохраните. Настройка общая для подразделений.
Миграция `0029_pyvrp_optimizer.sql` расширяет допустимые значения и сохраняет
имеющиеся настройки. Текущий выбранный метод автоматически не переключается.

Миграция `0030_supported_optimizers.sql` оставляет три поддерживаемых метода.
Ранее выбранный удалённый метод переводится на PyVRP; остальные настройки
сохраняются. Обновление его ревизии не позволяет публиковать устаревший черновик.
Общие функции подготовки расписания 2ГИС и сравнения назначений находятся в
`route-scheduling.ts`; этот модуль не выбирает исполнителей и не оптимизирует порядок.

Запуск из корня: `start-server.cmd`. Оба Python-решателя используют один сервис
на `127.0.0.1:8765`; зависимости перечислены в `services/optimizer/requirements.txt`.
Общий предел ожидания задаётся в настройках; поисковый бюджет на подразделение
сейчас 15 секунд. Ограничения протокола и инструкция отдельного развёртывания —
в `services/optimizer/README.md`.

Проверки: общий контракт обоих адаптеров, Python и HTTP, аварии, оборудование,
защищённые работы, публикация и сохранение/отмена настроек в браузере.
Приёмочный набор с замороженной дорожной матрицей можно запустить из `apps/web`:

```powershell
$env:OPTIMIZER_ACCEPTANCE_ENGINE='pyvrp'
node --test tests/beeline-planning.test.mjs
```

Он использует SQLite в памяти, не меняет рабочие назначения и не запускает
исследовательскую кампанию. Отчёт: `apps/web/.tmp/pyvrp-planning-acceptance.json`.

Документация библиотеки: [модель времени PyVRP 0.14](https://pyvrp.readthedocs.io/en/stable/notebooks/duration_constraints.html).
Её `release_time` означает момент отправления из депо; поэтому наш `releaseAt`
переводится в нижнюю границу окна обслуживания, а не в это поле библиотеки.
