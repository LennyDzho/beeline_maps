## 1. Вывод

Требуется адаптировать существующее планирование под правила кейса. Приоритетные изменения: подразделения, импорт исходных файлов, независимые временные окна, четыре вида транспорта, минимизация числа исполнителей, сравнение с базовым алгоритмом и объяснение результата.

Названия **Восток / Юго-восток / Югоцентр** используем как подразделения согласно указанию владельца проекта. По D-025 прежняя пользовательская сущность «Компания» теперь обозначает подразделение: каждое использует отдельную запись `organizations` и свой `organizationId`. Дополнительный уровень «компания → подразделения» не вводится. Принадлежность не следует автоматически из географии: например, подразделение «Юго-восток» включает Домодедово, Каширу и Ступино. Поле CSV «Район» сохраняется отдельно.

Переданные CSV содержат заявки и контрольные назначения, но не все данные, перечисленные в ТЗ. Владелец определил способ подготовки: названия бригад использовать в существующих карточках исполнителей, длительность рассчитать как среднее «Окончание − Начало» по типу HD, файлы сопоставлять по строке. Характеристики исполнителей задаются нашим тестовым сценарием. Смысл контроля и временных полей остаётся вопросом кейсодателю, поэтому расчёт по этим правилам не следует выдавать за восстановленную фактическую работу исходной системы.

После обновления приложения прежнее тестовое наполнение полностью заменяется новым. Новый набор: 205 заявок, из них 203 новые без назначений, одна отменена и одна выполнена согласно исключению дубля; 35 карточек исполнителей; три независимых подразделения с общим запуском и сводкой. Полный адрес берётся из контроля; квартира, подъезд и домофон становятся отдельными полями карточки. Мобильное приложение, FSM и дополнительные функции сохраняются.

**ТЗ не задаёт** точные веса или порядок предпочтения «меньше исполнителей / меньше километров» при конфликте этих двух критериев. Рекомендация для согласования: соблюдение ограничений и покрытие заявок, затем число исполнителей, затем километры. При недостатке ресурсов отдельно определить, как срочность соотносится с общим количеством назначенных заявок.

Количество диспетчеров и правила одновременного редактирования в ТЗ не заданы. Ручное переназначение в §2.5 относится к дополнительным возможностям. Владелец принял для нашего приложения D-025/D-026: общий расчёт по всем доступным подразделениям, общий черновик из согласованного снимка и атомарная проверка актуальности с применением всего плана. При чужих правках в любом участвующем подразделении публикация отклоняется с согласованным сообщением. Пулы заявок и исполнителей подразделений остаются раздельными. У диспетчера и администратора в фильтре заголовка должен быть пункт «Все подразделения»; фильтр меняет отображение, общий запуск охватывает все доступные подразделения. Это требования к будущей реализации, а не описание действующей защиты или интерфейса.

В §3.2 прямо указано, что мобильное приложение, авторизация, полноценная FSM-платформа и промышленная инфраструктура не обязательны. Владелец подтвердил, что эти функции сохраняются в продукте. Обновление общей модели и замена тестовых данных должны включать проверку Android, FSM и остальных действующих возможностей; необязательность по ТЗ не является основанием убрать их.

### 3.1. Объём и структура

Все шесть файлов имеют кодировку Windows-1251, разделитель `;`. Все строки заявок относятся к **17.08.2026**. Счёт ниже исключает две пустые строки и строку адреса офиса в конце каждого синтетического файла.

| Подразделение | Синтетические строки заявок | Строки контроля | Уникальные ID контроля | Непустые наименования исполнителей в контроле | Без исполнителя |
|---|---:|---:|---:|---:|---:|
| Восток | 66 | 66 | 66 | 12 | 2 |
| Юго-восток | 83 | 83 | 82 | 12 | 0 |
| Югоцентр | 56 | 56 | 56 | 11 | 0 |
| **Итого** | **205** | **205** | **204** | **34 по уникальному тексту имени** | **2** |

Сумма наименований по подразделениям равна 35; «Бригада Каушнян» встречается в Востоке и Юго-востоке. Поэтому 34 — число уникальных текстовых значений, а не установленная численность персонала исходной системы. По принятому Q-034 наша модель использует **35 независимых карточек исполнителей** с этими наименованиями, без отдельного состава бригад. Независимость подразделений подтверждена Q-037.

В синтетических данных **205 уникальных номеров заявок**. В каждом подразделении совпадают количество и последовательность строк заявок соответствующего контрольного файла по общим полям, если исключить ID и удалить квартирную часть адреса. Это наблюдение относится только к полученным версиям файлов.

Это способ подготовки тестов; смысл самих полей остаётся открытым Q-043. Окно и норматив хранятся раздельно.

Предложение по отображению BK на навыки:

- `Локальная заявка` → `Локальные работы`.

### 3.4. Существенные особенности контроля

1. **ID не совпадают с синтетикой.** Пересечение номеров каждой пары равно нулю. По рабочему решению владельца используем номер строки внутри пары, проверяя общие поля. Q-038/Q-039 остаются кейсодателю; воспроизводить историю и версии другой системы не требуется.
2. **Повтор номера `305898293` в Юго-востоке.** Строка 50: окно 20:00–22:00, статус «Отменена». Строка 57: окно 14:00–16:00, статус «Выполнена». Ответ Q-040: сохранить обе строки отдельно и перенести только для них соответствующие рабочие статусы. Синтетические номера — 24482 и 11872 соответственно.
3. **Неоднозначные составные ключи.** В Юго-востоке две пары строк имеют одинаковые общие поля после нормализации адреса: 13/14 и 75/79. Всего там 81 уникальный набор общих полей на 83 строки. Адрес + окно + тип не обеспечивает однозначного соответствия.
4. **Смешанные статусы.** В контроле: «Выполнена» — 112, «Отправлена» — 43, «Отменена» — 21, «В работе» — 11, «Просрочена» — 10, «В пути» — 6, «Не отправлена» — 2. По Q-003 это предположительно срез системы. Решение для загрузки: все 203 обычные строки — `new` без назначения, два исключения по Q-040 — `cancelled`/`completed`. Исходные статусы остаются атрибутами источника. Затем выполняется собственное планирование.
5. **Не задан порядок реального маршрута.** Порядок строк контроля нельзя считать порядком посещений, а начало окна — фактическим временем прибытия. Без этих данных нельзя вычислить фактический километраж контрольного дня.
6. **Объём превышает рекомендацию ТЗ.** В ТЗ предложено 10–15 инженеров и до 100 заявок; в файлах 205 строк. По Q-012 использовать весь набор, расчёты подразделений независимы. В первую оптимизацию идут 66/81/56 новых заявок, всего 203; два статусных исключения присутствуют в наборе, но не в очереди.

## 5. Три разных результата для сравнения

1. **Базовый алгоритм из ТЗ:** входной порядок заявок → первый допустимый инженер во входном порядке → добавление в конец его маршрута. Проверяются все обязательные ограничения. Глобальных перестановок нет.
2. **Рассчитанный системой план:** тот же вход, те же ограничения и матрицы; алгоритм улучшает число исполнителей и километраж.
3. **Контрольное распределение из CSV:** отдельный результат с пока неустановленной методикой. Для подготовки тестов применено соответствие по строке согласно решению владельца; Q-038/Q-039 остаются открытыми. Поле `baseline` в текущем программном контракте означает предыдущее назначение для определения изменений. Оно не реализует базовый алгоритм из ТЗ.

Нельзя заявлять экономию персонала за счёт меньшего числа назначенных заявок. В сравнении показываются покрытие, неназначенные заявки, нарушения, число уникальных исполнителей и километраж. Снижение километража при разном составе выполненных работ требует пояснения.
